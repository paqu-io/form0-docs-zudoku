form0-core validates schemas before running the engine. Validation focuses on structure and
attribute correctness, not UI concerns.

## What is validated

- Required attributes per field type
- Allowed values for attributes (for example, `display` options)
- Unique `key` and `data_name`
- `data_name` format (lowercase a-z, 0-9, underscore, max length 42)
- Default values match field type rules
- Condition operators are valid for the referenced field type
- AI metadata shape and allowed keys

## Runtime validation

At runtime, fields also validate their values when the engine evaluates:

- Numeric min/max checks
- Pattern matches for text fields
- Choice values must match defined choices

Runtime value validation runs for every field, including fields that are currently hidden. The
result is available in the engine state's `errors` map.

### Required fields and submission

The engine computes a `required` flag for each field, but it does not add an error merely because a
required field is empty. Required-field enforcement is a submission concern: the official
renderers combine `visible`, `required`, and the current value, skip hidden fields, and decide when
to display the error.

### Shared submission validation

`validateSubmission({ schema, snapshot, validationIssues })` checks an already evaluated runtime tree.
It does not evaluate values or establish freshness. `createRecordEvaluator().prepareSubmission()`
combines evaluation, selection and this same validation policy. Headless applications and renderer
integrations can share these submission rules.

Hidden fields and fields under hidden ancestors do not block ordinary submission. Visible required
read-only empty input fields do block. Numeric zero and legitimate false selections are populated
values. Intrinsic `state.errors` is unchanged, and LabelField/CalculatedField constraints remain.

The summary contains `hasErrors`, `requiredFieldErrors`, `generalErrors`, `scopeIssues` and
`orderedIssues`. Findings identify field key/data_name and full row `instancePath`; custom `INVALID`
remains scope-level. Root findings precede descendants in record order. `managedEvents: true` reruns
participating closed-row validators automatically. Genuine input failures require correction even
when many rows fail; root drafts remain allowed. Hidden record scopes do not participate. Root custom
rules remain root-level and cannot be automatically attributed to an individual hidden field.

Retained submissions validate the selected retained snapshot, including its calculated helpers and
condition outcomes. Their pending freshness is a separate fact. Validation handlers cannot write
values or perform UI operations; execution failures block eligibility, including drafts.

## Typical errors

- Missing required attributes
- Duplicate `key` or `data_name`
- Invalid operators (for example, `contains` on a numeric field)
- Default values that do not match the field type
