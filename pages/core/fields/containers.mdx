## Section

```json
{
  "type": "Section",
  "key": "details",
  "data_name": "details",
  "label": "Details",
  "display": "inline",
  "description": null,
  "description_mode": null,
  "visible": true,
  "visible_conditions": null,
  "elements": []
}
```

Additional attributes:

- `display`: `inline` or `drilldown`.
- `elements`: Nested fields.

## RepeatableSection

A `RepeatableSection` lets a user add any number of rows, such as the line items of an order. Each
row holds its own values for the same set of fields. In the output record, each row becomes a child
record.

```json
{
  "type": "RepeatableSection",
  "key": "items",
  "data_name": "items",
  "label": "Items",
  "display": "drilldown",
  "description": null,
  "description_mode": null,
  "visible": true,
  "visible_conditions": null,
  "location_enabled": false,
  "location_required": false,
  "title_field": {
    "type": "TitleField",
    "key": "@title",
    "data_name": "title",
    "label": "Title",
    "display": "default",
    "enabled": true,
    "visible": true,
    "visible_conditions": null,
    "read_only": true,
    "read_only_conditions": null,
    "elements": ["item_name", "item_date"]
  },
  "elements": [
    {
      "type": "TextField",
      "key": "item_name",
      "data_name": "item_name",
      "label": "Item name"
    },
    {
      "type": "DateField",
      "key": "item_date",
      "data_name": "item_date",
      "label": "Item date"
    }
  ]
}
```

Additional attributes:

- `location_enabled`: Enables location data for rows.
- `location_required`: Requires location data for rows.
- `title_field`: Optional `TitleField` used to derive each child record's title. Use `null` when no
  row title is configured.

Repeatable sections create an array of child records in the output. A configured row title is
stored as `@title` on each child record. If all title parts are blank, `@title` is `null`; renderers
may show a positional label such as `Items 1`, but that fallback is not persisted.

Title references are scoped to the repeatable's own child-record dataset. They may point to fields
inside ordinary nested `Section` containers, but not to fields outside the repeatable or inside a
nested `RepeatableSection`. Eligible types are `TextField`, `NumericField`, `DateField`, `TimeField`,
`SingleChoiceField`, `MultiChoiceField`, `BooleanField`, and `CalculatedField`. Ordered field keys are
preferred, while `data_name` references are accepted for authored schemas.

## BuildingPlanSection

```json
{
  "type": "BuildingPlanSection",
  "key": "building_plan",
  "data_name": "building_plan",
  "label": "Building plan",
  "description": null,
  "description_mode": null,
  "visible": true,
  "visible_conditions": null,
  "read_only": false,
  "read_only_conditions": null,
  "node_overrides": null
}
```

Additional attributes:

- `building_plan`: Compiler-generated topology and binding metadata; author questions through `node_overrides`.
- `node_overrides`: Overrides for generated nodes.
- `elements`: Generated nested RepeatableSections and their question definitions.

The example above is the hand-authored schema. Expansion adds `elements` and
`building_plan`; omit both when authoring this field. `elements` contains the actual generated
RepeatableSection hierarchy. `building_plan` describes its blueprint, generated keys, and bindings.
Neither attribute stores a respondent's drawn rooms or walls. Add custom questions through
`node_overrides`, rather than editing the generated `elements` tree.

The earlier example's `building_plan: { nodes: [], edges: [] }` and `elements: []` were redundant
placeholders that the expander replaced. They were not an instance-geometry format.

Geometry is saved in ordinary child records. In serialized output, each record's answers are under
`form_values`; floor, room, and wall collections contain child records with their own `form_values`.
The relevant generated fields are:

| Owner                         | Field before generated suffixes | Stored content                                                         |
| ----------------------------- | ------------------------------- | ---------------------------------------------------------------------- |
| Room                          | `room_vertices`                 | Versioned JSON text with metric polygon vertices and stable vertex IDs |
| Floor-owned physical wall     | `wall_geometry`                 | Versioned JSON text with metric construction segments                  |
| Room-facing wall row          | `wall_face_model`               | Versioned JSON text with physical-wall references and bound portions   |
| Floor, room, wall, or opening | Generated `*_model` fields      | Stable identities and relationship/default/override metadata           |

Actual output keys depend on expansion and the selected key mode. Opening dimensions and offsets
are ordinary numeric answers on wall-owned opening records. The record adapter reconstructs a
structured semantic snapshot from these fields; no separate schema-level geometry object is needed.

The canvas remains a view of ordinary repeatable records. Selecting an element opens its existing
row editor; Add, Edit, Save, Cancel, and Remove retain their usual roles. A child Save accepts into
its parent draft. Floor Save accepts into the form; record persistence still belongs to the host.
Cancelling a room or wall also reverses the shared geometry changes initiated in that editor.

Floors own physical walls and observations. Rooms own facing portions that reference those walls;
physical walls own their doors and windows. Columns, beams, and generic objects remain room-owned.
Two staggered rooms can share only 2 m of an 8 m continuous wall without creating another physical
wall. Physical subjects, vertices, segments, and facing portions have stable IDs separate from
repeatable row IDs and schema keys. Stored geometry uses metric coordinates.

The editing hierarchy remains floor → room → column/beam/object/wall → door/window.
The floor's canonical physical-wall and observation collections are internal storage, not separate
editors or navigation entries. Shared physical questions are shown in the ordinary room wall row.
An Observations child editor appears there only when observation questions are explicitly configured;
it is absent from the default workflow.

Custom wall questions belong to the room side by default. Use `node_overrides.walls.field_bindings`
to opt a custom question into another scope:

```js
field_bindings: {
  construction_material: { scope: 'physical_wall', inherit: true },
  surface_condition: { scope: 'room_face' },
  measured_moisture: { scope: 'observation' },
}
```

These names refer to ordinary question definitions in `walls.extra_elements`; retain their normal
field attributes. Physical answers are evaluated in the physical subject's context. Room questions
may read declared physical bindings. A physical calculation cannot take its meaning from one
room's private answers. Observation questions belong to explicit dated observation entries with
coverage and evidence; inherited defaults never create measurements or evidence.

Suitable properties can opt into live inheritance. Wall thickness and wall height initially support
it. Resolution is: explicit segment/wall override, then one distinct explicit adjacent-room default, then
floor fallback, then schema fallback. Equal room defaults agree; differing defaults require one
shared wall resolution. Height is never inferred from storey height. An explicit empty or unknown
answer is distinct from inheritance. Source labels show the effective value's origin; resetting an
override restores live inheritance. Requiredness and value checks apply to the effective value.

Canvas previews do not write accepted form state. Completed gestures commit one operation. Moving
a room detaches its shared sides and reconciles attachments at the destination. Shared-face edits
can adjust a neighbour over only the bound extent and create a valid local jog. Opening widths stay
fixed during ordinary stretches. Invalid geometry or openings leave the last valid layout intact
and report a conflict. Undo and Redo restore complete operations without replaying row lifecycle
events. Generic objects remain form-managed.

Each straight facing portion has its own ordinary wall row. A valid jog can turn four rows into
six. New runs receive separate physical wall identities by default; partial sharing alone does not
split a continuous wall. `editingPolicy: { preserveWallGrouping: true }` preserves physical grouping
for future operations, while keeping the separate facing rows. `separate_wall` can explicitly separate
selected construction segments (`wallId`, optional `segmentIds`). Neither choice describes a renovation
or creates new survey evidence. Surviving identities and source references are retained.

Magnetic alignment and gentle edge auto-pan are enabled by default and can be switched independently
with `editingPolicy.snapping` and `editingPolicy.edgeAutoPan`. CLI preview exposes these preferences
and physical grouping in Settings; React and Native show alignment and pan controls. Desktop Alt
bypasses snapping during a gesture. Guides account for wall thickness and zoom; stationary wall
extensions help remove tiny jogs. Pan stops on release/cancellation without changing zoom or
recentering. These are editor preferences, not record answers. Rejected edits show one recovery
message and retain the accepted layout. Scoped diagnostics remain available through the shared API.

Same-side parallel edges can align on a common line, including extensions; opposite shared faces
keep the wall-thickness gap. Compatible constraints can snap both axes during one move. A completed
compatible contact is reconciled as shared geometry; same-line alignment without contact does not
merge physical subjects. Captured walls extend to resized corners and shared junctions account for
thickness, including straight realignment and reversed returns.

A corner cutting partly through a door/window requires confirmation when the canvas gesture ends.
Cancel keeps the accepted layout. Confirm keeps the proposed position and removes the listed
physical openings from every room view; associated observation deletion is disclosed. Geometry,
opening removal, and any confirmed observation cascade form one Undo/Redo operation. A stale
confirmation cannot overwrite newer answers. An opening wholly outside the edited room's facing
extent stays on its surviving physical host. API hosts can provide `confirmOpeningRemoval` on the
canvas controller; its default declines removal. Ordinary row writes return the scoped conflict
without silently deleting an opening.

Save or cancel a separately open editor for an affected opening before repeating the move.

The portable APIs are exported from `form0-core` and `form0-core/building-plan`:

| API                                                  | Purpose                                                                            |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `createBuildingPlanSession`                          | Snapshots, previews, commits, checkpoints, history, and diagnostics                |
| `readBuildingPlanRecord` / `writeBuildingPlanRecord` | Canonical repeatable records and versioned semantic snapshots                      |
| `createBuildingPlanRecordSession`                    | Scoped row writes and effective-value presentation                                 |
| `createBuildingPlanEditor`                           | Existing nested editor lifetimes and shared transactions                           |
| `isBuildingPlanInternalCollection`                   | Presentation filter for canonical collections and unconfigured observation editors |

Use the metadata returned by `expandBuildingPlanSchema` rather than guessing generated field keys.
Room-side physical fields and hosted-opening lists are projections: standard serialization omits
those copies and retains the canonical floor/wall records once. Preserve the model identity and
geometry fields when storing or reloading a record. Canvas pan, zoom, selection, and unfinished
pointer/touch previews are transient UI state.

The raw record is verbose: generated keys identify fields, and geometry/model fields contain escaped
JSON text to preserve the ordinary field-value contract. For inspection or application processing,
decode a saved record into plain semantic objects:

```js
import {
  expandBuildingPlanSchema,
  buildFormRecordSnapshot,
  readBuildingPlanRecord,
} from "form0-core"

const expanded = expandBuildingPlanSchema(schema)
const runtime = buildFormRecordSnapshot(expanded.schema, savedRecord)
const plan = readBuildingPlanRecord({ meta: expanded.buildingPlanMeta[0], record: runtime })
// plan.floors[0].rooms[0].vertices
// plan.floors[0].walls[0].segments
```

This decoded view is reconstructed on demand; submission does not store another independent copy.
Coordinates are floor-local metres with x to the right and y down. A room-facing binding identifies
its wall/segment and the covered distance interval along that segment, so partial sharing is explicit.
