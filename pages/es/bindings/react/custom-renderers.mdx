Los renderers personalizados cambian la presentación sin sacar de `form0-core` los cálculos, la
visibilidad, la obligatoriedad ni la validación.

## Sustituciones acotadas

Usa preferentemente `FieldRegistryProvider` cuando una aplicación, una ruta, una prueba o una
historia de Storybook necesite un conjunto de renderers aislado:

```jsx
import { FieldRegistryProvider, FormRenderer } from "form0-react"
import { DateField } from "./date-field.jsx"

export function AppForm({ schema }) {
  return (
    <FieldRegistryProvider renderers={{ DateField }}>
      <FormRenderer schema={schema} />
    </FieldRegistryProvider>
  )
}
```

Un renderer recibe el mismo contrato de campo que usan los predeterminados:

```jsx
function DateField({ field, value, onChange, readOnly, inputProps, className }) {
  return (
    <input
      {...inputProps}
      className={className}
      type="date"
      value={value ?? ""}
      disabled={readOnly}
      onChange={(event) => onChange(event.target.value)}
    />
  )
}
```

Conserva las propiedades de accesibilidad que se proporcionan en `inputProps`.

## Instancias de registro y sustituciones globales

Usa `createFieldRegistry({ includeDefaults, renderers })` para crear una instancia de registro
explícita. Las funciones de módulo `registerFieldComponent`, `unregisterFieldComponent` y
`resetFieldComponents` modifican el registro predeterminado compartido, así que conviene reservarlas
para el arranque de la aplicación o las pruebas.

Solo se pueden registrar los tipos de campo que declara `form0-core`. Un tipo de campo nuevo en el
esquema debe definirse primero en el núcleo; un renderer de React por sí solo no puede ampliar el
contrato del esquema.
