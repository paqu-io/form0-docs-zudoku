form0-core valida los esquemas antes de ejecutar el motor. La validación se centra en la estructura y
en la corrección de los atributos, no en aspectos de la interfaz.

## Qué se valida

- Atributos obligatorios de cada tipo de campo
- Valores permitidos de los atributos (por ejemplo, las opciones de `display`)
- `key` y `data_name` únicos
- Formato de `data_name` (minúsculas a-z, 0-9, guion bajo, longitud máxima de 42)
- Que los valores predeterminados cumplan las reglas del tipo de campo
- Que los operadores de las condiciones sean válidos para el tipo de campo referenciado
- Estructura y claves permitidas de los metadatos de IA

## Validación en tiempo de ejecución

Durante la ejecución, cada campo comprueba su valor cuando el motor evalúa el formulario. El
resultado está en el mapa `errors` del estado del motor.

| Campo            | Valor aceptado                                                            | También se comprueba                                          |
| ---------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `TextField`      | Un texto                                                                  | `pattern`, si está definido                                   |
| `NumericField`   | Un número finito                                                          | `min` y `max`, y números enteros cuando `format` es `integer` |
| `DateField`      | Una fecha real del calendario como `YYYY-MM-DD`, del año `0001` al `9999` | Nada más                                                      |
| `TimeField`      | `HH:MM` o `HH:MM:SS`, con horas `00`–`23` y minutos y segundos `00`–`59`  | Nada más                                                      |
| Campos de opción | Valores definidos en `choices`                                            | Nada más                                                      |

- form0 no convierte valores, así que `"12"` en un `NumericField` es un error.
- `null`, `undefined` y `""` cuentan como vacíos, no como un tipo incorrecto. Un `TextField`
  opcional vacío también omite `pattern`.
- Un valor que falla sigue en `values` y aparece en `errors`, así que un registro cargado se puede
  inspeccionar y corregir.
- Estas comprobaciones se aplican a todos los campos, incluidos los ocultos.

### Pruébalo

Necesitas [form0-cli](/es/cli/install-update).

1. Descarga un formulario con un `TextField`, un `NumericField` y un `DateField`:

   ```bash
   curl -o value-types.json https://docs.form0.dev/examples/value-types.form0.json
   ```

1. Ejecútalo con valores correctos. La salida muestra `"errors": {}`:

   ```bash
   form0 run value-types.json --values '{"name":"Ada","age":36,"start":"2026-02-28"}'
   ```

1. Ejecútalo con valores incorrectos:

   ```bash
   form0 run value-types.json --values '{"name":42,"age":"36","start":"2026-02-30"}'
   ```

   Ahora cada campo aparece en `errors`:

   ```json
   "errors": {
     "name": "name must be a string",
     "age": "age must be a finite number",
     "start": "start must be a valid YYYY-MM-DD date"
   }
   ```

### Campos obligatorios y envío

El motor calcula un indicador `required` para cada campo, pero no añade un error solo porque un
campo obligatorio esté vacío. La comprobación de campos obligatorios forma parte del envío: los
renderers oficiales combinan `visible`, `required` y el valor actual, omiten los campos ocultos y
deciden cuándo mostrar el error.

### Comprobar un envío

`createRecordEvaluator().prepareSubmission()` ejecuta los cálculos, selecciona los valores que se
enviarán y aplica las mismas comprobaciones que los renderers oficiales. Úsalo en un servidor o en
cualquier aplicación sin renderer. Consulta sus opciones en
[Preparar un envío](/es/core/engine/evaluation-cycle#preparar-un-envío).

Si ya tienes un snapshot evaluado, llama a
`validateSubmission({ schema, snapshot, validationIssues })`. Solo comprueba: no recalcula nada ni
elimina campos desconocidos.

Ambos siguen las mismas reglas:

- De forma predeterminada, los campos ocultos y los campos bajo padres ocultos no bloquean un envío.
- Un campo obligatorio visible y vacío bloquea el envío, aunque sea de solo lectura.
- `0` y un **No** seleccionado cuentan como rellenados.
- Una [fila oculta de una sección repetible](/es/core/fields/containers#repeatablesection) no
  participa en la comprobación.
- Un borrador se puede guardar con errores de validación. Un manejador que falla durante la
  ejecución también bloquea los borradores.
- Los manejadores de validación no pueden cambiar valores ni mostrar alertas.
- Estas comprobaciones no cambian `state.errors`. `LabelField` y `CalculatedField` siguen sus
  propias reglas.

El resultado incluye un `validationSummary`:

| Propiedad             | Contiene                                                                                  |
| --------------------- | ----------------------------------------------------------------------------------------- |
| `hasErrors`           | Si algo ha fallado.                                                                       |
| `requiredFieldErrors` | Campos obligatorios vacíos.                                                               |
| `generalErrors`       | Valores que no cumplen las reglas de su campo.                                            |
| `scopeIssues`         | Mensajes de `INVALID()`, que pertenecen a un registro o una fila, no a un campo.          |
| `orderedIssues`       | Todo lo anterior en el orden del registro, con el registro principal antes que sus filas. |

Cada hallazgo identifica su campo por clave y `data_name`, y su fila por `instancePath`. Un mensaje
de `INVALID()` del registro principal se queda en el registro principal, porque form0 no puede saber
a qué campo se refiere. `managedEvents: true` también ejecuta los manejadores de validación de las
filas cerradas. Todas las filas que fallan deben corregirse antes de que el envío pase, sean las que
sean.

Si un usuario conserva valores calculados anteriores durante una
[revisión](/es/core/engine/evaluation-cycle#revisar-filas-modificadas), las comprobaciones se
aplican a esos valores conservados, incluidas las condiciones que dependen de ellos.

### Comprobar valores ocultos en un servidor

De forma predeterminada, un envío ignora los errores de los campos ocultos, porque el usuario no
puede verlos. Un cliente que llama a tu API puede poner cualquier cosa en esos campos, así que
activa la comprobación en el código de tu servidor:

```js
const result = await evaluator.prepareSubmission(snapshot, { validateHiddenValues: true })
```

`validateSubmission()` acepta la misma opción. Con ella activada, un valor oculto que no cumple sus
propias reglas bloquea el envío, como un número en un `TextField`. Esto incluye las filas ocultas.
Las demás reglas no cambian:

- Un campo obligatorio oculto y vacío no bloquea, y los manejadores de validación de las filas
  ocultas no se ejecutan.
- Un borrador se puede seguir guardando con estos errores.
- Cuando continúes una revisión con `decision`, pasa el mismo ajuste.

Cada uno de estos errores tiene `hidden: true`. Para reemplazar o borrar el valor desde tu código,
consulta
[Resolver un valor oculto](/es/core/engine/evaluation-cycle#resolver-un-valor-oculto-que-no-pasa-la-validación).

Esta comprobación solo cubre valores. No elimina campos desconocidos ni decide quién puede enviar.
[Añade un formulario a una aplicación React existente](/es/guides/add-form-to-react-app) incluye un
ejemplo completo de servidor.

## Errores típicos

- Atributos obligatorios ausentes
- `key` o `data_name` duplicados
- Operadores no válidos (por ejemplo, `contains` en un campo numérico)
- Valores predeterminados que no coinciden con el tipo de campo
