Los manejadores de eventos permiten que un esquema reaccione a lo que ocurre en un formulario, como
la carga de un registro o el cambio de un campo. Un manejador nunca modifica el formulario
directamente. Describe lo que debe ocurrir como una lista de operaciones, y el renderer o tu aplicación las aplica. Esta página explica cómo se registran los manejadores, qué pueden leer y cómo se aplican sus
operaciones.

Para saber qué eventos despachan los renderers oficiales, consulta
[Despacho de eventos en los bindings oficiales](/es/core/builtins/events-overview).

## Registrar manejadores

El código de `form.events.code` se ejecuta una vez, al crear el motor. Cada llamada a `ON` registra
un manejador y cada llamada a `OFF` elimina uno:

```js
ON("change", "age", function onAgeChange(event) {
  if ($age >= 18) {
    SETVALUE("adult_note", "Adult")
  }
})

ON("change", function onAnyChange(event) {
  // Runs for every field
})

ON("load-record", function onLoad() {
  ALERT("Welcome", "Review the details before editing.")
})
```

- Los bindings oficiales identifican el campo por su `data_name`, así que los manejadores de los
  eventos de campo que despachan los bindings también deben registrarse con el `data_name`. El core
  compara la cadena de registro de forma exacta y no traduce entre `key` y `data_name`.
- Omite el campo para ejecutar el manejador en todos los campos.
- Un tipo de evento desconocido muestra un aviso y el manejador no se registra.
- `ON` y `OFF` dentro de un manejador surten efecto cuando el despacho termina bien. Si el despacho
  se rechaza, no hacen nada. Los callbacks anidados dentro de un manejador funcionan en Hermes, pero
  no pueden usar las variables locales del manejador exterior.

## Cómo se ejecuta el código de los manejadores

El motor conserva el código fuente de cada manejador definido en `form.events.code` y ejecuta ese
código cada vez que se despacha el evento. Por eso, un manejador no puede usar variables del código
que lo rodea: las constantes, variables y funciones declaradas en el nivel superior de
`form.events.code` no están disponibles dentro del manejador.

```js
const ADULT_AGE = 18

ON("change", "age", function onAgeChange(event) {
  // Fails with "ADULT_AGE is not defined"
  if ($age >= ADULT_AGE) {
    SETVALUE("adult_note", "Adult")
  }
})
```

Dentro de un manejador, lee los valores del formulario con `$data_name`. Para la lógica que
comparten varios manejadores, pasa una función en la opción `helpers` del motor.

Los manejadores deben ser síncronos. Si un manejador es `async` o devuelve una promesa, el motor
emite un aviso y `trigger()` devuelve solo las operaciones que el manejador creó antes de su primer
`await`. Las operaciones creadas después se descartan con un aviso, y un error lanzado después de un
`await` se notifica en lugar de escapar del motor. Estos avisos se muestran en la consola en
desarrollo y llegan a los manejadores de `WarningSystem` que hayas registrado.

Como el motor conserva el código fuente por su cuenta, los manejadores también se ejecutan en
Hermes, el motor de JavaScript de React Native, que no expone el código fuente de las funciones.
Esto funciona con declaraciones de función, expresiones de función y funciones flecha escritas en
`form.events.code`, incluidas las que se asignan a una variable y se pasan a `ON` más adelante.

Para cualquier otro callback, el motor lee el código fuente con `toString()`. Esto incluye los
callbacks que proceden de `helpers`, los métodos de objeto, los
getters y setters, y los miembros de clase. Funciona en Node.js y en los navegadores, pero no en
Hermes. Allí, el motor muestra `Event callback source is unavailable` y ejecuta los demás
manejadores.

## Cuándo se ejecutan los manejadores

Un manejador solo se ejecuta cuando se despacha su evento, ya sea desde un binding o desde tu
aplicación con `engine.trigger(eventType, fieldDataName, metadata)`. Crear el motor o ejecutar
`eval()` no despacha eventos.

En un mismo despacho, primero se ejecutan los manejadores registrados para ese campo, en el orden en
que se registraron. Después se ejecutan los manejadores registrados para todos los campos. Si un
manejador lanza un error, el motor muestra `[form0] Expression evaluation failed` en la consola y
los demás manejadores se siguen ejecutando.

## Qué puede leer un manejador

Un manejador lee los valores de los campos con `$data_name`, como un cálculo. Ve los valores del
momento en que se despachó el evento. En un evento `change` de un renderer oficial, eso ocurre
después de la pasada de evaluación que siguió a la edición, así que los campos calculados ya están
actualizados.

Los campos que puede leer un manejador dependen del evento:

- **Los eventos de registro**, como `load-record` y `edit-record`, solo pueden leer campos del
  formulario principal.
- **Los eventos de campo**, como `change`, siguen las mismas reglas que un cálculo definido en el
  campo que los desencadenó. Consulta [Ámbitos padre e hijo](/es/core/engine/parent-child-scopes).

Cada manejador recibe también un objeto `event` con `type`, `fieldKey` (el `data_name` del campo) y
`timestamp`, además de cualquier metadato pasado a `trigger()`. Los renderers oficiales añaden el
nuevo `value` y la definición `field` a los eventos `change`.

Los manejadores pueden usar los builtins de expresión compartidos, como `IF` y `CHOICEVALUE`, además
de los builtins de eventos. Los builtins exclusivos de los cálculos, como `SETRESULT`, no están
disponibles.

<Callout type="info" title="SETVALUE no actualiza lo que lee el manejador">
  `SETVALUE` solo registra una operación. Durante el resto del manejador, `$data_name` sigue
  devolviendo el valor del momento en que se despachó el evento. El nuevo valor es visible después
  de aplicar la operación.
</Callout>

## Operaciones

`SETVALUE` y `ALERT` añaden cada uno una operación a la lista que devuelve `engine.trigger()`:

```js
// SETVALUE("adult_note", "Adult")
{ type: "FIELD_OPERATION", operation: "SETVALUE", params: { fieldDataName: "adult_note", valueToSet: "Adult" } }

// ALERT("Welcome", "Review the details before editing.")
{ type: "UI_OPERATION", operation: "ALERT", params: { title: "Welcome", message: "Review the details before editing." } }
```

Las operaciones de todos los manejadores de un mismo despacho se devuelven juntas, en el orden en
que se ejecutaron los manejadores.

### Las operaciones se comprueban antes de devolverse

Antes de que `trigger()` devuelva su resultado, el motor comprueba cada `SETVALUE` según el ámbito
del manejador. Si uno apunta a un campo que el manejador no puede escribir, o a un campo que no está
en el esquema, el motor informa de una advertencia y `trigger()` no devuelve ninguna operación de
ese evento. Cada `SETVALUE` que devuelve `trigger()` apunta a un campo que el manejador puede
cambiar.

### Cómo aplican las operaciones los bindings oficiales

De forma predeterminada, los renderers oficiales:

- muestran cada `ALERT` en su propio cuadro de diálogo; y
- escriben el valor de cada `SETVALUE` en el formulario y ejecutan una nueva pasada de evaluación.

<Callout type="caution" title="Los campos de opción aceptan identificadores de texto">
  `SETVALUE` acepta un identificador de texto para un `SingleChoiceField` o `BooleanField`, y una
  lista de identificadores de texto para un `MultiChoiceField`. Si un valor tiene una forma
  incorrecta, no se aplica ninguna operación de ese evento, y el renderer registra `Event failed.`
  en la consola. Consulta la [referencia de `SETVALUE`](/es/core/builtins/events/setvalue).
</Callout>

Los componentes `FormRenderer` de React y React Native permiten que una aplicación gestione las
operaciones que no son alertas mediante `engineOptions.onOperations`. Cada renderer presenta sus
operaciones `ALERT` y pasa las demás operaciones a tu callback.

```js
function onOperations(operations, meta, applyDefault) {
  // meta is { eventType, fieldKey, metadata }
  console.log(`${meta.eventType} returned ${operations.length} operations`)
  applyDefault(operations, meta)
}
```

Llama a `applyDefault` con las operaciones que quieras que el binding gestione como de costumbre.

### Aplicar operaciones sin un renderer

Si usas form0-core directamente, aplica tú la lista devuelta. Para `SETVALUE`, llama a
`engine.setValue(fieldDataName, valueToSet)`, que acepta un identificador de texto para un campo de
opción y ejecuta la evaluación. Consulta [Ciclo de evaluación](/es/core/engine/evaluation-cycle).

## Sin cadenas de eventos de cambio

Aplicar un `SETVALUE` ejecuta una nueva pasada de evaluación, pero no despacha `change` para el campo
que asignó. Un manejador `change` de `age` que asigna `adult_note` no ejecuta los manejadores
`change` de `adult_note`.

Si asignar un campo también debe activar la lógica de otro, pon ambas en el mismo manejador o usa un
`CalculatedField` cuando el valor pueda derivarse de otros campos.

## Obtener resultados detallados

`engine.trigger()` devuelve solo las operaciones. Usa
`engine.triggerDetailed(eventType, fieldKey, metadata)` cuando también necesites los mensajes de
validación y los fallos. Es síncrono y devuelve tres listas:

```js
const { operations, validationIssues, issues } = engine.triggerDetailed("validate-record")
```

- `operations`: lo que hay que aplicar. Si un manejador falla, está vacía.
- `validationIssues`: mensajes de `INVALID()`.
- `issues`: fallos durante la ejecución de los manejadores, cada uno con `code`, `message`,
  `eventType` e `instancePath`.

Ninguno de los dos métodos evalúa el formulario, guarda un registro ni cierra un editor.

### Ejecutar los manejadores de una fila

Para ejecutar los manejadores de una fila sin renderer, pasa `eventScope.instancePath` al crear el
motor. La ruta del registro principal es `[]`. Cada segmento de fila tiene `repeatableKey`,
`instanceId`, `index` e `identity`. Las rutas usan las claves del esquema, y los listeners usan
`data_name`. Una fila sin identificador usa `identity: "position"`. form0 comprueba la ruta con el
esquema, pero tu aplicación debe comprobar que la fila sigue existiendo.

Un manejador de fila puede leer sus propios campos, y los campos de filas padre y del formulario
principal que aporte tu aplicación. `SETVALUE()` solo escribe en la fila actual. Las filas hermanas,
las filas hijas y las colecciones repetibles quedan fuera de su alcance. Los metadatos no pueden
sustituir las propiedades propias del evento, como su tipo o su ámbito.

### Qué puede hacer cada tipo de manejador

| Manejadores                              | Pueden                      | No pueden                                                |
| ---------------------------------------- | --------------------------- | -------------------------------------------------------- |
| `validate-record`, `validate-repeatable` | Llamar a `INVALID(message)` | Cambiar valores, mostrar alertas ni devolver promesas    |
| `cancel-record`, `cancel-repeatable`     | Leer valores                | Cambiar valores, llamar a `INVALID()` ni mostrar alertas |
| `unload-record`, `unload-repeatable`     | Leer valores                | Cambiar valores, llamar a `INVALID()` ni mostrar alertas |

`save-record` y `save-repeatable` se ejecutan antes de guardar. No existen eventos de esquema
`saved-*`. Las aplicaciones se encargan de guardar, de los mensajes de éxito y de cerrar el editor.

Los metadatos de un evento pueden contener objetos simples, listas, fechas, valores simples y
referencias `File` o `Blob`, que conservan sus metadatos y su contenido. Los demás tipos de objeto
se rechazan. Los manejadores del esquema no pueden ser asíncronos.

Consulta el
[contrato de eventos mantenido](https://github.com/paqu-io/form0-core/blob/development/EVENT_CONTRACT.md)
para ver las reglas completas.

## Registros de solo lectura

Cada manejador recibe `event.mode`, que es `"readonly"` o `"edit"` para el registro en el que se
ejecuta. Una fila de solo lectura dentro de un registro editable recibe `"readonly"`. El modo es
independiente de si el registro es nuevo, de si es un borrador y del ajuste `read_only` de un campo.
Los metadatos y los manejadores no pueden cambiarlo.

`load-record` se ejecuta una vez cada vez que se abre un registro, en cualquier modo. Un registro
abierto para editar ejecuta `new-record` o `edit-record` después. Pasar de solo lectura a edición
ejecuta `edit-record` sin volver a ejecutar `load-record`.

En un registro de solo lectura, los manejadores pueden leer valores, mostrar un `ALERT` y añadir o
quitar listeners. Un `SETVALUE` rechaza todo el lote, incluidas las alertas y los cambios de
listeners, y el registro sigue siendo legible. `triggerDetailed()` lo informa en `issues`, y
`trigger()` no devuelve operaciones e informa de una advertencia.

Pon la inicialización que debe ejecutarse siempre que empieza la edición en un manejador de
`new-record` o `edit-record`, no en `load-record`. Los helpers que tu aplicación pasa al motor
pueden tener sus propios efectos secundarios, que form0 no puede deshacer.
