## Section

```json
{
  "type": "Section",
  "key": "details",
  "data_name": "details",
  "label": "Details",
  "display": "inline",
  "description": null,
  "description_mode": null,
  "visible": true,
  "visible_conditions": null,
  "elements": []
}
```

Atributos adicionales:

- `display`: `inline` o `drilldown`.
- `elements`: campos anidados.

## RepeatableSection

Una `RepeatableSection` permite al usuario añadir cualquier número de filas, como las líneas de un
pedido. Cada fila guarda sus propios valores para el mismo conjunto de campos. En el registro de
salida, cada fila se convierte en un registro hijo.

```json
{
  "type": "RepeatableSection",
  "key": "items",
  "data_name": "items",
  "label": "Items",
  "display": "drilldown",
  "description": null,
  "description_mode": null,
  "visible": true,
  "visible_conditions": null,
  "location_enabled": false,
  "location_required": false,
  "title_field": {
    "type": "TitleField",
    "key": "@title",
    "data_name": "title",
    "label": "Title",
    "display": "default",
    "enabled": true,
    "visible": true,
    "visible_conditions": null,
    "read_only": true,
    "read_only_conditions": null,
    "elements": ["item_name", "item_date"]
  },
  "elements": [
    {
      "type": "TextField",
      "key": "item_name",
      "data_name": "item_name",
      "label": "Item name"
    },
    {
      "type": "DateField",
      "key": "item_date",
      "data_name": "item_date",
      "label": "Item date"
    }
  ]
}
```

Atributos adicionales:

- `location_enabled`: habilita los datos de ubicación de las filas.
- `location_required`: exige datos de ubicación para las filas.
- `title_field`: `TitleField` opcional que se usa para obtener el título de cada registro hijo. Usa `null` si no
  hay ningún título de fila configurado.

Las secciones repetibles generan un array de registros hijos en la salida. El título de fila configurado se
guarda como `@title` en cada registro hijo. Si todas las partes del título están vacías, `@title` es `null`; los renderers
pueden mostrar una etiqueta posicional como `Items 1`, pero ese valor alternativo no se guarda.

Las referencias del título se limitan al conjunto de datos de los registros hijos de la propia sección repetible. Pueden apuntar a campos
dentro de contenedores `Section` anidados normales, pero no a campos fuera de la sección repetible ni dentro de otra
`RepeatableSection` anidada. Los tipos admitidos son `TextField`, `NumericField`, `DateField`, `TimeField`,
`SingleChoiceField`, `MultiChoiceField`, `BooleanField` y `CalculatedField`. Se recomiendan las claves de campo ordenadas,
aunque en los esquemas escritos a mano también se aceptan referencias por `data_name`.

## BuildingPlanSection

Al modificar una esquina compartida, las paredes adyacentes no editadas conservan su alineación.
Su longitud puede ajustarse en la unión. Fijar un tramo protege además sus extremos.

Las habitaciones empiezan como rectángulos. Arrastre una esquina para modificar sus dos tramos
adyacentes, incluidas paredes diagonales y esquinas de habitaciones divididas o con retranqueos.
Al arrastrar una pared, esta permanece paralela a su orientación inicial. El arrastre de paredes
diagonales del perímetro sigue la dirección horizontal o vertical inicial; las paredes adyacentes
conservan su dirección y ajustan su longitud en las nuevas intersecciones. Las esquinas también
siguen una guía horizontal o vertical. Mantenga Alt para moverse libremente en ambos ejes, o use
**Free drag** en Native. Los tabiques interiores divididos mantienen su regla de movimiento perpendicular.
Elija **Pin / unpin** y después una pared para fijar su posición durante la sesión de edición actual.
Las fijaciones son controles del editor, no respuestas guardadas. Los cambios compartidos se
previsualizan juntos y usan Save, Cancel y Undo/Redo habituales del elemento y de la planta.
El ajuste de contacto reconoce el espesor físico de la pared a distintos niveles de zoom.

```json
{
  "type": "BuildingPlanSection",
  "key": "building_plan",
  "data_name": "building_plan",
  "label": "Building plan",
  "description": null,
  "description_mode": null,
  "visible": true,
  "visible_conditions": null,
  "read_only": false,
  "read_only_conditions": null,
  "node_overrides": null
}
```

Atributos adicionales:

- `building_plan`: metadatos de topología y vínculos generados por el compilador; las preguntas se definen mediante `node_overrides`.
- `node_overrides`: modificaciones que se aplican a los nodos generados.
- `elements`: RepeatableSections anidadas y definiciones de preguntas generadas.

El ejemplo anterior es el esquema escrito por el autor. La expansión añade `elements` y
`building_plan`; omitir ambos al definir este campo. `elements` contiene la jerarquía real de
RepeatableSections generadas. `building_plan` describe su plantilla, claves generadas y vínculos.
Ninguno almacena las habitaciones o paredes dibujadas por el usuario. Añadir preguntas mediante
`node_overrides`, sin editar el árbol `elements` generado.

Los anteriores `building_plan: { nodes: [], edges: [] }` y `elements: []` eran marcadores redundantes
que el expansor sustituía. No eran un formato para la geometría de una respuesta.

La geometría se guarda en registros hijos normales. Las respuestas de cada registro serializado
están en `form_values`; las colecciones de plantas, habitaciones y paredes contienen registros
hijos con su propio `form_values`. Los campos generados relevantes son:

| Propietario                             | Campo antes de los sufijos generados | Contenido guardado                                                                           |
| --------------------------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------- |
| Habitación                              | `room_vertices`                      | Texto JSON versionado con vértices métricos del polígono e identificadores estables          |
| Pared física de la planta               | `wall_geometry`                      | Texto JSON versionado con tramos constructivos métricos                                      |
| Fila de cara de pared de una habitación | `wall_face_model`                    | Texto JSON versionado con referencias a la pared física y porciones vinculadas               |
| Planta, habitación, pared o abertura    | Campos `*_model` generados           | Identidades estables y metadatos de relaciones, valores predeterminados y valores explícitos |

Las claves reales dependen de la expansión y del modo de claves elegido. Las dimensiones y
posiciones de las aberturas son respuestas numéricas normales en sus registros hijos de pared.
El adaptador reconstruye una instantánea semántica estructurada; no hace falta otro objeto de
geometría en el esquema.

<Callout type="info" title="Contrato experimental de BuildingPlan">
  Este contrato se desarrolla en versiones coordinadas de core, CLI, React y Native. No se migran
  automáticamente los registros con el formato de desarrollo anterior. No se incluye exportación IFC
  ni RDF.
</Callout>

El lienzo representa registros repetibles normales. Seleccionar un elemento abre su editor de fila;
Add, Edit, Save, Cancel y Remove conservan su función habitual. Save en un hijo acepta cambios en el
borrador del padre. Save en la planta acepta cambios en el formulario; la aplicación sigue siendo
responsable de guardar el registro. Cancelar una habitación o pared también revierte los cambios
compartidos de geometría iniciados en ese editor.

Las plantas contienen las paredes físicas y las observaciones. Las habitaciones contienen las
porciones de cara que referencian esas paredes; las puertas y ventanas pertenecen a la pared física.
Columnas, vigas y objetos genéricos siguen perteneciendo a la habitación. Dos habitaciones desplazadas
pueden compartir solo 2 m de una pared continua de 8 m. Los sujetos físicos, vértices, segmentos y
porciones tienen identificadores estables distintos de los de las filas y del esquema. Las coordenadas son métricas.

La jerarquía de edición sigue siendo planta → habitación → columna/viga/objeto/pared → puerta/ventana.
Las colecciones canónicas de paredes físicas y observaciones de la planta son almacenamiento interno,
sin editores ni entradas de navegación independientes. Las preguntas físicas compartidas se muestran
en la fila habitual de pared de la habitación. El editor hijo Observations solo aparece allí cuando
se configuran explícitamente preguntas de observación; no forma parte del flujo predeterminado.

Las preguntas personalizadas de pared pertenecen por defecto al lado de la habitación. Usa
`node_overrides.walls.field_bindings` para elegir otro ámbito:

```js
field_bindings: {
  construction_material: { scope: 'physical_wall', inherit: true },
  surface_condition: { scope: 'room_face' },
  measured_moisture: { scope: 'observation' },
}
```

Los nombres corresponden a preguntas normales de `walls.extra_elements`, con sus atributos
habituales. Las respuestas físicas se evalúan en el contexto del sujeto físico. Las preguntas de
habitación pueden leer vínculos físicos declarados. Un cálculo físico no puede depender de
respuestas privadas de una habitación. Las observaciones tienen fecha, cobertura y evidencia
explícitas; los valores heredados nunca crean mediciones ni evidencia.

Las propiedades adecuadas pueden activar la herencia dinámica. Inicialmente se incluyen el espesor
y la altura de pared. La precedencia es: valor explícito del tramo o de la pared, un único valor explícito distinto
de las habitaciones adyacentes, valor de planta y valor de esquema. Los valores iguales coinciden;
los distintos exigen una resolución compartida en la pared. La altura nunca se deduce de la altura
de planta. Un vacío o desconocido explícito se distingue de heredar. Las etiquetas muestran el
origen; restablecer un valor explícito recupera la herencia. La obligatoriedad y validación se aplican al valor efectivo.

Las previsualizaciones no escriben el estado aceptado. Cada gesto completo confirma una operación.
Mover una habitación separa sus lados compartidos y reconcilia las conexiones en el destino. Editar
una cara compartida puede ajustar solo la extensión vinculada del vecino y crear un quiebro válido.
El ancho de las aberturas se conserva en estiramientos normales. La geometría inválida mantiene la
última disposición válida y muestra un conflicto. Undo y Redo restauran operaciones completas sin
repetir eventos de ciclo de vida. Los objetos genéricos se gestionan desde el formulario.

El lienzo dibuja el material de cada pared con su espesor efectivo, incluidos los valores explícitos
de los tramos, y muestra cada abertura una sola vez a través de esa franja. Las filas de cara siguen
siendo los destinos de selección y edición. Las uniones válidas se dibujan sin trazos internos
duplicados; dibujar una unión no fusiona identidades ni respuestas. Un espesor explícitamente
desconocido se representa con una línea esquemática discontinua, sin inventar una anchura. Estas
formas se calculan y no se guardan en el registro. La CLI prioriza la habitación que se está editando
si las porciones se superponen; React y Native limitan la edición a la habitación activa. La vista
inicial incluye el material exterior junto al origen; los gestos posteriores no la recentran. Por defecto, un
cambio de espesor fija la cara de la habitación activa, o la cara de referencia estable para cambios
de planta. Pasar de 0,20 m a 0,30 m mantiene esa cara y desplaza la opuesta 0,10 m, sujeto a validación.
Los valores explícitos de habitación contradictorios siguen exigiendo una resolución común en la pared.

Cuando un nuevo retorno de un quiebro alcanza una pared existente, el contacto compatible comparte
ese elemento físico. La cara de la habitación activa queda fija y la opuesta se separa por el
espesor efectivo, sin duplicar la franja. Su fila de cara puede llevar la etiqueta de la pared existente.
Al separar una habitación, se reconcilian las extensiones guardadas de la pared estacionaria con sus
caras restantes, conservando identidad, posiciones de aberturas y contexto de observaciones fechadas.
Se conservan las particiones creadas de forma independiente y la longitud necesaria para alojar aberturas retenidas.

Cada porción recta de cara tiene su propia fila normal de pared. **Split** crea porciones editables
explícitas de una pared recta, conservando su identidad física, aberturas y observaciones originales.
Elija un punto con alineación magnética o introduzca una distancia desde el extremo marcado `0`.
El corte permanece al enderezar y al
guardar/recargar. **Rejoin** elimina el corte elegido cuando las porciones son contiguas, colineales
y tienen respuestas compatibles. Las porciones desplazadas o respuestas contradictorias muestran
una explicación; se rechaza un corte por una abertura. Cada comando es una operación reversible
dentro del borrador normal. React y Native los ofrecen en la habitación activa; en Native,
seleccione una pared en modo Select para introducir la distancia exacta. La sesión acepta
`split_face` (`faceId`, `offset` en metros) y `rejoin_cut` (`cutId`). Los vértices métricos guardan
la referencia `editingCutId`; `split_wall` / `join_walls` siguen siendo operaciones físicas distintas.
En una porción dividida explícitamente, el único campo **Thickness** existente modifica ese tramo
físico. No hay otro campo de espesor ni una pregunta de alcance. Las caras compartidas muestran el
mismo valor; el resto conserva su espesor efectivo. Las sobrescrituras se guardan en segmentos de
construcción; los valores por defecto siguen activos y Reset restaura la herencia. Por defecto, la cara activa
queda anclada y la opuesta puede formar un escalón al cambiar el espesor. Rejoin conserva las
divisiones significativas de espesor. Las demás preguntas físicas mantienen su alcance declarado.
Las guías magnéticas también usan bordes inmóviles de la misma habitación y sus prolongaciones,
para que los retornos válidos puedan enderezarse exactamente.
Las porciones de tabiques interiores se mueven perpendicularmente al tramo original, manteniendo
retornos conectados. Use Rejoin antes de mover o modificar el tabique completo. Guarde o cancele
una entrada de pared abierta antes de eliminarla con Rejoin.

Un quiebro válido puede pasar de cuatro filas a seis. Los nuevos tramos independientes reciben
identidades físicas distintas por defecto; compartir solo una parte no divide una pared continua.
`editingPolicy: { preserveWallGrouping: true }` conserva
la agrupación física en operaciones futuras, manteniendo las filas de cara separadas. `separate_wall`
permite separar explícitamente tramos (`wallId`, `segmentIds` opcional). Estas decisiones no describen
una reforma ni generan pruebas de medición. Se conservan identidades y referencias de origen.

Las ediciones locales usan los ejes físicos conectados antes de derivar caras y material. Las líneas
de apoyo adyacentes no editadas permanecen fijas; sus extremos pueden deslizarse. La agrupación física
no decide la propagación ni el recorte. Los tabiques interiores intencionales siguen visibles. Ejes,
vínculos de cara y vértices interiores mantienen el contrato de registro de versión 1; la red de
uniones se deriva y no se guarda como otro grafo.

`editingPolicy.thicknessAnchor` elige `'room_face'` (predeterminado) o `'midline'`. El primero fija la
cara de la habitación activa, o la cara de referencia estable en un cambio de toda la planta. El
segundo fija el eje y desplaza ambas caras la mitad del cambio de grosor. Settings de CLI incluye
esta opción en Building Plan Editing; web/Native usan el valor definido en código sin otro control
visible estándar. Se aplica a futuras ediciones, incluidas las respuestas de grosor en filas normales.
Cambiar la preferencia no modifica geometría ni historial Undo. Las observaciones no cambian.

La alineación magnética y el desplazamiento suave cerca de los bordes están activados por defecto;
`editingPolicy.snapping` y `editingPolicy.edgeAutoPan` los controlan de forma independiente. Settings
incluye esas preferencias y la agrupación física en CLI; React y Native muestran controles de alineación
y desplazamiento. Alt omite la alineación durante un gesto de escritorio. Las guías tienen en cuenta
espesor y zoom; las prolongaciones estáticas ayudan a eliminar pequeños quiebros. El desplazamiento
termina al soltar o cancelar, sin cambiar zoom ni centrar la vista. Son preferencias del editor, no
respuestas. Un rechazo muestra un mensaje de recuperación y conserva la geometría aceptada. La API
compartida mantiene los diagnósticos por ámbito.

La alineación de paredes usa sus ejes y prolongaciones cuando hay geometría de eje. Las caras
opuestas de igual grosor conservan esa separación; los tramos de grosor distinto alinean sus ejes,
sin forzar las caras interiores sobre una línea. Un movimiento puede alinear ambos ejes. Un contacto
compatible se reconcilia como geometría compartida; la alineación sin contacto no fusiona elementos
físicos. Las paredes alcanzan las nuevas esquinas y las uniones consideran el espesor, incluso al
recuperar una línea recta o invertir un retorno.

Una esquina que corta parcialmente una puerta o ventana requiere confirmación al terminar el gesto.
Cancelar conserva la disposición aceptada. Confirmar conserva la posición propuesta y elimina las
aberturas físicas indicadas de todas las vistas; se informa de cualquier eliminación de observaciones.
La geometría y las eliminaciones confirmadas forman una sola operación Undo/Redo. Una confirmación
obsoleta no sobrescribe respuestas nuevas. Una abertura totalmente fuera de la cara de la habitación
editada permanece en su pared física. Los hosts pueden proporcionar `confirmOpeningRemoval` al
controlador; por defecto rechaza eliminar. Las escrituras normales de filas devuelven el conflicto
por ámbito sin eliminar aberturas de forma silenciosa.

Guarde o cancele cualquier editor abierto de una abertura afectada antes de repetir el movimiento.

Las API portables se exportan desde `form0-core` y `form0-core/building-plan`:

| API                                                  | Función                                                                                     |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `createBuildingPlanSession`                          | Instantáneas, previsualizaciones, confirmación, puntos de control, historial y diagnósticos |
| `readBuildingPlanRecord` / `writeBuildingPlanRecord` | Registros repetibles canónicos e instantáneas semánticas versionadas                        |
| `createBuildingPlanRecordSession`                    | Escrituras de fila acotadas y presentación del valor efectivo                               |
| `createBuildingPlanEditor`                           | Ciclo de los editores anidados existentes y transacciones compartidas                       |
| `isBuildingPlanInternalCollection`                   | Filtro de presentación para colecciones canónicas y editores de observación sin configurar  |

Usa los metadatos de `expandBuildingPlanSchema` para resolver claves generadas. Los campos físicos
y listas de aberturas mostrados desde una habitación son proyecciones: la serialización normal
omite esas copias y conserva una sola vez los registros canónicos. Conserva los campos de identidad
y geometría al guardar o recargar. Desplazamiento, zoom, selección y gestos sin terminar son estado transitorio.

El registro sin procesar es extenso: las claves generadas identifican campos, y los campos de
geometría/modelo contienen texto JSON escapado para conservar el contrato habitual de valores.
Para inspección o procesamiento, decodifica el registro guardado en objetos semánticos ordinarios:

```js
import {
  expandBuildingPlanSchema,
  buildFormRecordSnapshot,
  readBuildingPlanRecord,
} from "form0-core"

const expanded = expandBuildingPlanSchema(schema)
const runtime = buildFormRecordSnapshot(expanded.schema, savedRecord)
const plan = readBuildingPlanRecord({ meta: expanded.buildingPlanMeta[0], record: runtime })
// plan.floors[0].rooms[0].vertices
// plan.floors[0].walls[0].segments
```

Esta vista se reconstruye bajo demanda; el envío no guarda otra copia independiente.
Las coordenadas son metros locales de la planta, con x hacia la derecha e y hacia abajo. Cada vínculo
de cara identifica su pared/segmento y el intervalo de distancia cubierto a lo largo del segmento,
por lo que las partes compartidas quedan explícitas.
