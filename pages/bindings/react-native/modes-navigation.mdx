## Interaction mode and actions

Set `mode="edit"` or `mode="readonly"`. A read-only form exposes the built-in edit action;
`showPrimaryActionsInViewMode` controls its visibility.

The built-in header shows submit or save according to `primaryActionMode`. Set `showHeader={false}`
when the application provides its own screen header and actions. `onRequestClose` enables cancel
behavior and protects dirty forms with a discard confirmation.

## Repeatable entry opening mode

`repeatableEntryMode` accepts `readonly` (default) or `edit` for existing rows at every nesting
level. Existing rows open in view mode with Edit when their parent permits editing; new rows start
in edit mode. A read-only parent allows browsing descendants while preventing editing, adding and
removing them. The direct-edit option does not override parent restrictions.

View displays supplied accepted calculated values without running calculations or applying missing
schema defaults. Conditions and intrinsic validation still use those values. Edit evaluates with
current permitted ancestor values. With accepted child totals 110/220 and root 330, viewing keeps
110/220; editing line 1 produces 120, saving it makes root 340, and cancelling keeps root 330.
Working values selected before a failed persistence callback remain unsaved work when returning to View.

Managed opening awaits `load-record`/`load-repeatable`, then the matching new/edit event for direct
editing. View → Edit runs edit without repeating load. `event.mode` is `readonly` or `edit` for the
executing record, independent of its parent's mode. View permits reads, ALERT and scoped ON/OFF;
a record write rejects the complete operation batch before host delegation. Move writable
initialization to new/edit, or guard load setters for direct editing. This requires the coordinated
core release with mode control; it changes no form-schema or saved-record shape.

## Sections and validation

`FormRenderer` owns:

- inline and drilldown section navigation;
- repeatable-section list and editor screens;
- a navigation sheet for sections and validation issues;
- movement to the first invalid field after a failed submission;
- keyboard-aware scrolling to focused or invalid fields.

`forceShowNavigationPanel` makes the navigation entry point available even when the current form
structure would not normally require it. `keyboardScrollOffset` adjusts the vertical destination
for application headers or other overlays.

`labelPosition` accepts `top` or `side`; use `labelWidthPercent` to size the label column in side
layout. Keep conditional navigation behavior in the schema instead of duplicating it in component
state.

## Record events and repeatable entries

With `engineOptions.events.lifecycle: true`, the host must specify `recordKind: "new"` or
`"existing"` for the root. Opening runs `load-record`; entering editing runs `new-record` or
`edit-record`. Rows use their actual classification and the corresponding `*-repeatable` events.
View mode runs load only and preserves accepted calculations; conditions and intrinsic validation still evaluate.

The default legacy opt-out preserves earlier lifecycle behavior. See the managed lifecycle
contract in [FormRenderer](/bindings/react-native/form-renderer) and
[Events and operations](/core/engine/events-operations).
