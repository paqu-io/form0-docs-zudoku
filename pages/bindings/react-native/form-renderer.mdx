`FormRenderer` validates and prepares a schema, creates the form engine, renders native fields and
sections, and produces structured records or restorable snapshots.

```jsx
<FormRenderer
  schema={schema}
  initialValues={{ name: "Ada" }}
  mode="edit"
  colorMode="light"
  labelPosition="top"
  onSubmit={saveRecord}
/>
```

## Essential properties

| Property              | Purpose                                                                                            |
| --------------------- | -------------------------------------------------------------------------------------------------- |
| `schema`              | A form0 schema containing `form.elements`.                                                         |
| `initialValues`       | Initial non-repeatable field values.                                                               |
| `initialSnapshot`     | Restore raw values, repeatable state, and timestamps together.                                     |
| `overrideValues`      | Apply authoritative values over initial values.                                                    |
| `onSubmit`            | Receive a validation-gated structured record and metadata.                                         |
| `onSave`              | Receive a snapshot without requiring the form to be valid.                                         |
| `onSnapshotChange`    | Observe seed and user-change snapshots.                                                            |
| `mode`                | Start in `edit` or `readonly` mode.                                                                |
| `repeatableEntryMode` | Opening mode for existing repeatable rows: `readonly` (default) or `edit`; new rows start editing. |

## Host integration

- `onRequestClose` enables the root cancel action and receives `{ reason: "cancel" }` after any
  required discard confirmation.
- `headerAccessory` renders application content immediately below the built-in header.
- `showHeader` hides the built-in header when the host owns surrounding navigation and actions.
- `primaryActionMode`, `primaryActionLabel`, and `showPrimaryActionsInViewMode` customize the
  built-in primary action.
- `onSchemaReady` receives the prepared schema after stable keys have been ensured.
- `engineOptions` supplies Core helpers, security configuration, warnings, operation handling, and
  update observation.

Schema event handlers run on Hermes when they are written as functions or arrow functions in
`form.events.code`. See [How handler code runs](/core/engine/events-operations#how-handler-code-runs).

Continue with [Values, snapshots, and submission](/bindings/react-native/values-snapshots-submission)
or [Modes and navigation](/bindings/react-native/modes-navigation).

## Engine options and calculation diagnostics

`engineOptions` forwards helpers, security, `onWarning`, `onUpdate`, `onOperations`, and calculation diagnostic controls to root and repeatable-row engines. Helpers and security are engine-construction settings: remount `FormRenderer` to replace them predictably. Callbacks and the console preference stay current in already-open editors without an extra evaluation.

```jsx
const findingsByScope = new Map()

;<FormRenderer
  schema={schema}
  engineOptions={{
    diagnostics: { console: false },
    onDiagnostics(snapshot, meta) {
      if (meta.kind === "scope-ended") findingsByScope.delete(meta.scopeId)
      else findingsByScope.set(meta.scopeId, { snapshot, meta })
    },
  }}
/>
```

Console reporting is enabled by default. `diagnostics.console: false` suppresses calculation details, recovery and scope-ended console notices; collection and callbacks remain active. Providing `onDiagnostics` does not implicitly disable console reporting. Core codes, severity, messages, phases, suggestions and context are preserved. Developer console headings use English, as with the existing binding messages.

`onDiagnostics(snapshot, meta)` receives a defensive array after each accepted completed evaluation, including the first, identical findings and `[]` after recovery. Console output suppresses identical repeats and reports new/changed findings, recovery and recurrence. Errors from diagnostic observers, including rejected promises, cannot interrupt evaluation or operation processing.

Metadata contains `scopeId`, `instancePath`, `evaluationId` and `kind`. A scope identifies one transient engine lifetime; evaluation IDs increase within that scope. Root paths are `[]`. Each row path segment contains `repeatableKey`, `instanceId`, zero-based `index`, and `identity: "id" | "position"`. Existing `id` or `record_id` values are used, with an explicitly positional fallback when absent. Findings carry the same path in `context.instancePath`; reporting never creates record IDs.

Closing/deleting an editor, replacing its engine/schema, or unmounting retires the old scope with `onDiagnostics([], { ...meta, kind: "scope-ended" })`. This means the scope is no longer observed, not that the saved row recovered. Only engines that actually evaluate are represented: the callback is not a complete submission-health report and does not re-evaluate closed rows.

Calculation diagnostics remain outside `state.errors`, saved snapshots and record payloads. They do not change validation display timing, submission decisions or draft saving, and do not create automatic alerts or a diagnostics panel.

`onOperations(operations, meta, applyDefault)` receives non-alert operations. Delegate selected operations with `applyDefault(selected, meta)`; without a callback, existing default processing remains active. Renderer-owned `ALERT` dialogs appear once. Operation batches follow the existing platform processing; callbacks must handle every supplied batch. `onWarning` remains the legacy warning route, including its existing throttling, and is not a replacement for diagnostic snapshots. `onUpdate(state, engine)` retains the execution-specific engine/facade argument; use `onDiagnostics` for portable diagnostic consumption.

## Managed events and custom validation

This integration requires form0-react-native 0.5.0 or newer and core 0.5.1 or newer. Expanded automatic lifecycle events are opt-in:

```jsx
<FormRenderer
  schema={schema}
  engineOptions={{
    events: { lifecycle: true, recordKind: "existing", fieldInteractions: ["focus", "blur"] },
    onEventController: (controller) => {
      controllerRef.current = controller
    },
  }}
/>
```

`recordKind` must explicitly be `new` or `existing`; values never determine it. Configuration is
fixed for an editor session; remount to change classification, lifecycle, helpers or security.
Callbacks remain live. Without opt-in, automatic root load/edit/change behavior is preserved.
Readonly opening runs load only; editable opening runs load then new/edit. Open rows use the
repeatable equivalents and their actual classification.

The generation-bound controller is delivered after initialization and retired with `null`.
`dispatch({ type, fieldKey?, instancePath?, scopeId?, metadata? })` returns a promise with `status`,
`operations`, `validationIssues` and `issues` after accepted operation work finishes.
`prepareSave({ intent: 'submit' | 'draft', instancePath?, scopeId? })` returns a promise with
`eligible`, `payload`, `meta`, `validationSummary` and `issues`. It never persists or closes.
Field listeners use `data_name`; paths use schema keys and existing row IDs. Positional fallback
requires the observed active `scopeId` from diagnostics. Closed targets and old generations are rejected.

`INVALID(message)` creates a nonempty synchronous scope-level message during validate-record or
validate-repeatable. Custom findings join the existing validation summary/navigation, replace each
attempt and clear on editable changes or retirement. They never enter intrinsic `state.errors`,
calculation diagnostics, values or record/media metadata. Validation and close handlers reject value/UI
operations and promises. Row handlers can read current main/ancestor fields, but SETVALUE writes only
in their current row; collection access is excluded.

Preparation waits for updates, validates, runs save-\* once when policy allows, awaits operations,
revalidates changed values and serializes that final snapshot. Submit and row acceptance respect
validation; root drafts remain allowed with `hasErrors: true`. Row drafts are unsupported. Execution
failure returns no payload. `isDraft` describes the current action; `isValid` is intrinsic validity.
Calculation diagnostics alone never block saving. Closed-row freshness and aggregation remain separate.

User edits emit contextual change after updates settle. Accepted row membership changes include
`action` (add/edit/remove) and `affectedInstancePath`; enabled status fields emit user-only change-status.
Defaults, SETVALUE and calculations do not emit additional change. Extra interactions default to none;
built-in text/numeric controls support focus/blur/click (Native click means input press). Other controls
may dispatch explicitly. Async onOperations work and selective applyDefault work are awaited; the
fallback expires with its dispatch. Alerts remain renderer-owned and occur once.

Confirmed cancel runs cancel then unload; supported successful closes run unload before disposal.
Hosts closing directly must dispatch unload before unmounting. Rerenders, resets, Strict Mode cleanup
and forced unmount only retire scopes. Save-_ is pre-save; no saved-_ schema events are added.
Applications own persistence, success notifications and closing.

Native File/Blob uploads preserve standard metadata and immutable data. Their custom properties are outside native serialization. The media compatibility correction is included in core 0.5.1.
