## Initial state and restoration

Use `initialValues` for an ordinary record seed. `overrideValues` take precedence and suit
authoritative host values. For complete restoration, prefer `initialSnapshot`:

```jsx
<FormRenderer
  engineOptions={{ events: { recordKind: "existing" } }}
  schema={schema}
  initialSnapshot={savedDraft}
  onSnapshotChange={(snapshot, change) => {
    if (change.dirty) queueLocalDraft(snapshot)
  }}
  onSubmit={uploadRecord}
/>
```

The snapshot keeps raw values, nested repeatable entries, and timestamps together:

```js
{
  raw_values: {},
  repeatable: {},
  timestamps: {
    created_at_client: null,
    updated_at_client: null,
    created_at_server: null,
    updated_at_server: null,
  },
}
```

`onSnapshotChange(snapshot, meta)` first reports `{ kind: "seed", dirty: false }`; later user
changes use `{ kind: "change", dirty }`.

## Save failures and console messages

When a save fails, `FormRenderer` keeps the user's values so they can retry, and prints one
`console.error` report with the failure stage and the original error. It does not show a message to
the user, so do that in your application and then rethrow the error:

```jsx
async function handleSubmit(record) {
  try {
    await saveRecord(record)
  } catch (error) {
    setMessage("The record was not saved. Try again.")
    throw error
  }
}
```

If you catch the error without rethrowing it, `FormRenderer` treats the save as successful.

`submissionDiagnostics` controls these console messages:

```jsx
<FormRenderer
  schema={schema}
  engineOptions={{ events: { recordKind: "new" } }}
  submissionDiagnostics={{ saveFailures: true, validationBlocks: false }}
  onSubmit={handleSubmit}
/>
```

- `saveFailures` is on by default. Set it to `false` if your application already reports failures.
- `validationBlocks` is off by default. Set it to `true` to log one line each time validation blocks
  **Submit** or a repeatable row's **Save**.

A required field left empty is a validation block, not a save failure.

### Try it

1. Tap **Submit** with a required field empty. The field shows its validation message, and the
   console stays quiet.
2. Add `validationBlocks: true` and tap **Submit** again. The console shows
   `[form0-react-native] Submit blocked by validation.`
3. Fill in the field, make `saveRecord` throw `new Error("Example save failure")`, and tap
   **Submit**. The console shows `[form0-react-native] Submit failed during onSubmit.` with your
   error, and your values stay in the form.
4. Remove the `throw` and tap **Submit** again. The save succeeds.

### Details

- These settings take effect immediately, even while a save is pending. They are separate from
  `debug`, `engineOptions.diagnostics.console`, and lifecycle settings.
- Reports do not include form values, snapshots, or record paths. Preparation failures include their
  issue codes and messages.
- Cancelling a confirmation stays quiet. An exception thrown by your callback is reported as a
  callback failure.
- `form0-core` prints its own lines, such as `[EVENT HANDLER] Registered`. These settings do not
  control them.
- These settings cover the renderer's built-in actions. If you call `prepareSave()` directly,
  inspect the result it returns.
- The same settings apply to draft `onSave` failures. Invalid drafts stay saveable, and a successful
  draft save logs no validation block.

## Save drafts or submit records

Set `primaryActionMode="save"` and provide `onSave(snapshot, meta)` for a validation-tolerant draft
action. `meta` contains the current validation summary and dirty state.

The default submit action validates first. `onSubmit(record, meta)` receives the structured record
described in [Output and records](/core/output-records), plus raw values, repeatable state,
timestamps, and the validation summary.

The binding does not persist or synchronize either payload. Store snapshots locally, upload
records, retry failures, and resolve conflicts in the host application.

## Managed event API

See the managed event controller and scope contract in [FormRenderer](/bindings/react-native/form-renderer).

`engineOptions.events`: `lifecycle` (true), required `recordKind` (new/existing), `fieldInteractions` ([focus, blur, click]). Set `lifecycle: false` for legacy lifecycle or `fieldInteractions: []` to disable automatic interactions.
`engineOptions.onEventController(controller | null)`: `dispatch(request)`, `prepareSave(request)`.

Preparation does not persist or close. Root draft validation findings remain visible in the returned summary; normal submit and row acceptance are blocked by validation failures. Calculation diagnostics remain independent. No closed-row evaluation or aggregation is added.

## Child calculation review and persistence

Ordinary submission automatically refreshes closed-child calculations when the form setting is
omitted. `form.repeatable_recalculation: 'confirm'` requires review. Host `mode: 'confirm'` may
strengthen that requirement; `automatic` cannot weaken an authored confirmation. `allowRetain` is
explicit host permission and does not enable confirmation by itself. Review choices apply to all
affected children or none. A root save is rejected while a child editor is still unaccepted.

The default review shows row titles/paths, field labels, old/new values and counts in bounded pages.
Override review/status text with `submissionOptions.messages`. Complete validation findings remain
available with record paths; the UI pages them and navigates to the affected record or field.
Scope-level custom findings belong to their record, with no invented field association.

```jsx
<FormRenderer
  engineOptions={{ events: { recordKind: "existing" } }}
  schema={schema}
  initialSnapshot={savedSnapshot}
  initialFreshness={savedFreshness}
  submissionOptions={{ mode: "confirm", allowRetain: true }}
  onSubmit={async (record, meta) => {
    await storage.save({ record, freshness: meta.freshness })
  }}
/>
```

A successfully completed callback acknowledges persistence. It must save the selected record and
matching freshness companion together before resolving; throw or reject on failure or cancellation.
Selecting `20 → 24` keeps `24` as unsaved editor work even if validation or persistence then fails.
Freshness stays outside saved form values. Restore the host's persisted companion through
`initialFreshness`; older acknowledgements cannot clear newer pending state. For retained child
totals `[110,220]`, the submitted root sum is `330`, never the refreshed proposal's `360`.

Prepare-only controllers do not open a dialog or persist data. Check `eligible`, handle
`requires_decision` with `payload: null`, and acknowledge only the exact successfully saved
`preparationId`. Change pages default to 50 and allow at most 100 entries. Continue a review by calling
`prepareSave()` with `decision: { reviewId, action: 'refresh' | 'retain' | 'cancel' }`. Changed inputs,
configuration or a newer preparation invalidate the review. Validation runs before the save hook,
which executes once per attempt; accepted hook writes can require a new review without repeating it.

```js
const prepared = await controller.prepareSave({ intent: "submit", signal })
if (prepared.status === "requires_decision") {
  const page = await controller.getSaveChanges({
    preparationId: prepared.preparationId,
    offset: 0,
    limit: 50,
  })
  showReview(prepared, page)
} else if (prepared.eligible) {
  await storage.save({ record: prepared.payload, freshness: prepared.meta.freshness })
  controller.acknowledgeSave({ preparationId: prepared.preparationId })
}
```

Root `prepareSave({ intent: 'draft' })` and the Native draft save action preserve accepted child
calculations without a dialog. Ordinary validation failures remain reportable and permit a root
draft; execution failures prevent it. Apply the same record-plus-companion persistence contract to
`onSave`. A successful durable offline write is separate from later server synchronization.

Programmatic setters use the shared strict input contract. Initial values and host overrides remain tolerant loading paths, including View; accepted calculations are preserved in View. [See the value-update contract](/core/engine/value-updates).
