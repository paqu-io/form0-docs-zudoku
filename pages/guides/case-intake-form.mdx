In this guide, you build a support case intake form and run it in the React and Vite starter. The
form has:

- contact fields that appear, and become required, based on the preferred contact method;
- a priority calculated from the answers;
- a response date calculated from the priority; and
- a business impact field that is required only for high-priority cases.

All of this behavior lives in one JSON schema. The application code only registers the form.

**Time:** about 15 minutes.

## Before you start

- **Node.js** `22.19.0+`
- **form0-cli**, installed with `npm install --global form0-cli`

## How it works

### Conditional fields

The **Email** field is hidden by default. Its conditions show it, and make it required, when the
contact method is `email`:

```json
{
  "data_name": "email",
  "visible": false,
  "visible_conditions": {
    "field_id": "contact_method",
    "operator": "equal_to",
    "value": "email"
  },
  "required_conditions": {
    "field_id": "contact_method",
    "operator": "equal_to",
    "value": "email"
  }
}
```

A condition on a choice field compares the selected choice `value`, not its label. See
[Conditions and operators](/core/schema/conditions-operators).

Hiding a field does not clear its value. If someone types an email address and then switches to
**Phone**, the email address is still in the form values. Decide in your application whether hidden
values should be kept.

### Calculated priority

`priority` is a `CalculatedField`. Its `calculate` expression reads the answers to **Who is
affected?** and **Is work blocked?**:

```js
IF(
  !CHOICEVALUE($impact),
  null,
  IF(
    CHOICEVALUE($blocked) === "yes" || CHOICEVALUE($impact) === "organization",
    "high",
    IF(CHOICEVALUE($impact) === "team", "normal", "low"),
  ),
)
```

`CHOICEVALUE()` returns the selected value of a choice field. The first `IF()` keeps the priority
empty until **Who is affected?** has an answer.

The expressions on this page are split across lines for readability. In the schema, each one stays
on a single line: a calculation that spans several lines returns nothing unless you wrap its result
in [`SETRESULT()`](/core/builtins/calculations-expressions/setresult).

### Response date

`respond_by` adds a number of days to `received_on`, based on the priority:

```js
DATEADD(
  $received_on,
  IF($priority === "high", 1, IF($priority === "normal", 3, IF($priority === "low", 7, null))),
)
```

[`DATEADD()`](/core/builtins/calculations-expressions/dateadd) returns `null` when the number of
days is blank, so the date stays empty until there is a priority. `"display": { "style": "date" }`
tells the renderer to format the result as a date.

### A condition driven by a calculation

**Describe the business impact** uses the same kind of condition as **Email**, but it reads
`priority`, which is itself calculated:

```json
{
  "data_name": "business_impact",
  "visible": false,
  "visible_conditions": {
    "field_id": "priority",
    "operator": "equal_to",
    "value": "high"
  },
  "required_conditions": {
    "field_id": "priority",
    "operator": "equal_to",
    "value": "high"
  }
}
```

This works because the engine runs calculations before it evaluates conditions.

## What just happened

Each time you changed an answer, the starter's renderer passed it to the form0 engine. The engine
re-ran `priority` and then `respond_by`, in dependency order, and then re-evaluated which fields are
visible and required. The renderer only displayed the result. The same schema produces the same
behavior in any application that uses form0.
