Exécutez `form0 serve [schema]` pour lancer le serveur d’aperçu local. Par défaut, il utilise le
port `3030` et écoute sur `localhost` ; `--port` et `--host` permettent de modifier ces valeurs.

Le serveur d’aperçu est un outil de développement. Utilisez des projets et des connecteurs de
confiance, et ne l’exposez que sur un réseau de confiance.

## Diagnostics de calcul dans le navigateur

Dans form0-cli 0.6.0 et les versions ultérieures, le serveur renvoie des diagnostics structurés avec l’état
évalué. La console affiche les problèmes nouveaux ou modifiés, résolus et récurrents ; les
évaluations identiques ne les répètent pas. Les diagnostics des lignes imbriquées indiquent le
chemin répétable et l’ID existant de la ligne, ou une référence explicite par position sans ID.

Utilisez `form0 serve [schema] --no-diagnostics` pour masquer les rapports de calcul de la CLI
et la sortie console de l’aperçu intégré. Les diagnostics restent collectés. Une application
lancée avec `serve --app` conserve sa propre politique de présentation.

Une évaluation terminée renvoie l’état même si ses diagnostics contiennent des erreurs. La
validation des champs, les opérations d’événement, la soumission et les brouillons conservent
leur comportement ; les diagnostics n’ajoutent pas d’alertes ni de blocages de soumission.

## Événements portables de l’aperçu (CLI 0.7.0+)

L’aperçu intégré actuel utilise l’évaluation partagée de core et nécessite core 0.8.1 ou ultérieur
dans la branche compatible 0.8.x. Les nouveaux aperçus activent le cycle de vie et sélectionnent
**Nouvel enregistrement**. Dans **Paramètres du formulaire → Aperçu de l’enregistrement**, choisissez
**Enregistrement existant** ou **Ouvrir en lecture seule**. La classification choisit les hooks ;
elle ne charge aucun enregistrement de la base de données. Les désactivations explicitement
sauvegardées restent respectées. **Paramètres avancés des événements** contient le commutateur de
compatibilité et les abonnements facultatifs de focus, blur et clic. L’ouverture en lecture seule
exécute uniquement load ; changer la configuration démarre une nouvelle session avec les valeurs
acceptées. `serve --app` conserve les options de l’application. React et Native proposent ces options
par API, sans cette interface ; leur activation explicite par défaut reste inchangée.

L’initialisation évalue les valeurs effectives, exécute `load-record`, puis `new-record` ou
`edit-record`. Les changements utilisateur attendent les mises à jour en file ; valeurs par défaut,
calculs et `SETVALUE()` ne produisent pas de changements supplémentaires. Le statut activé utilise
`change-status` ; focus/blur texte et numérique et clic sur les liens compatibles sont facultatifs.

L’envoi suit validation intégrée/personnalisée → `save-record` une fois → nouvelle validation
uniquement si les valeurs changent → sérialisation finale → envoi au connecteur existant.
`INVALID(message)` synchrone crée un message de résumé du périmètre sans modifier `state.errors`.
Les diagnostics de calcul ne bloquent pas seuls l’envoi. **Préparer le brouillon** affiche un
instantané et un résumé éventuellement invalide dans la console, sans persistance ni connecteur.
Il n’y a aucun événement de schéma `saved-*`.

Les lignes intégrées proposent **Modifier**, **Enregistrer la ligne** et **Annuler la ligne**. Elles
utilisent les événements repeatable et des valeurs provisoires : enregistrer valide/prépare avant
acceptation ; annuler abandonne les modifications imbriquées provisoires. Lecture des champs
principaux/ancêtres autorisés, écritures limitées à la ligne. Réduire est uniquement visuel. Les
ajouts/modifications/suppressions acceptés notifient le repeatable propriétaire ; les erreurs de
notification ultérieures restent distinctes de la préparation acceptée. Les lignes fermées utilisent la préparation partagée décrite ci-dessous sans rejouer leur cycle d’édition.

Le contrôleur actif est `window.form0PreviewEvents`. `dispatch()` et
`prepareSave({ intent: 'submit' | 'draft' })` renvoient des promesses avec résultats/problèmes et
attendent la présentation acceptée ; préparer n’envoie ni ne ferme. Les lignes exigent un
`instancePath` complet et le `scopeId` observé (`data-preview-scope-id`) ; les chemins positionnels
exigent cet ID. Les métadonnées sont JSON ; fonctions et fichiers natifs sont rejetés. Aucune
métadonnée de périmètre/diagnostic n’entre dans les valeurs enregistrées. Annuler/Fermer notifie avant
retrait ; rechargement/destruction forcée retire uniquement. Rouvrir crée une nouvelle session.
Les codes de sortie de run/validate restent inchangés.

**Actions avancées de l’aperçu** regroupe **Préparer le brouillon**, **Annuler l’enregistrement** et
**Fermer l’enregistrement** dans une section repliée. Préparer un brouillon permet de l’inspecter et
ne le sauvegarde jamais via un connecteur. Les contrôles désactivés des lignes imbriquées indiquent
quel éditeur parent ouvrir d’abord. L’envoi affiche l’objet final dépliable et le résultat de chaque
connecteur dans la console. Sans connecteur, il indique que l’enregistrement est préparé uniquement
pour l’aperçu ; un échec de connecteur ou de stockage ne constitue pas une sauvegarde réussie.

## Préparation partagée et adaptateur de stockage du host

L’aperçu utilise la fraîcheur et la validation intégrée partagées, avec ou sans cycle de vie géré.
La désactivation laisse les hooks et la validation personnalisée gérés désactivés. Aucun événement
load/edit/change/save/unload de ligne fermée n’est rejoué. Acceptez ou annulez les éditeurs enfants
avant la préparation racine.

`createApp()` accepte `submissionOptions` côté serveur et un `storageAdapter` facultatif. Conserver
exige cet adaptateur et `allowRetain` ; le navigateur ne peut pas accorder cette permission.
L’adaptateur implémente `load(identity)` asynchrone retournant `{ record, freshness }` ou `null`, et
`save(identity, { record, freshness })`. `record` garde la structure existante. La session restaure
`recordIdentity` ou `recordOptions.mainRecordId`, y compris zéro. L’exemple remplace atomiquement une
enveloppe locale ; le host de production définit la gestion des révisions et conflits.

La réussite reconnaît la préparation. Un rejet, une persistance partielle ou l’échec d’un connecteur
laisse la tentative non enregistrée. Les connecteurs reçoivent le même enregistrement sans devoir
stocker la fraîcheur. Les clients de préparation reconnaissent explicitement leur sauvegarde externe.
`getSaveChanges()` pagine les changements ; les choix concernent tous les enfants ou aucun.

```js
import { createApp } from "form0-cli/src/server/express-server.js"
import { createFilePreviewStorage } from "form0-cli/src/server/preview-events/file-storage.js"

const app = createApp(getSchema, getSchemaSource, projectDir, {
  submissionOptions: { mode: "confirm", allowRetain: true },
  storageAdapter: createFilePreviewStorage(previewStorageDirectory),
})
```
