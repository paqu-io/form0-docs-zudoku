Les gestionnaires d'événements permettent à un schéma de réagir à ce qui se passe dans un
formulaire, comme le chargement d'un enregistrement ou la modification d'un champ. Un gestionnaire
ne modifie jamais directement le formulaire. Il décrit ce qui doit se passer sous forme d'une liste
d'opérations, et le renderer ou votre application les applique. Cette page explique comment les gestionnaires sont
enregistrés, ce qu'ils peuvent lire et comment leurs opérations sont appliquées.

Pour savoir quels événements les renderers officiels déclenchent, voir
[Déclenchement des événements dans les bindings officiels](/fr/core/builtins/events-overview).

## Enregistrer des gestionnaires

Le code de `form.events.code` s'exécute une fois, à la création du moteur. Chaque appel à `ON`
enregistre un gestionnaire, et chaque appel à `OFF` en supprime un :

```js
ON("change", "age", function onAgeChange(event) {
  if ($age >= 18) {
    SETVALUE("adult_note", "Adult")
  }
})

ON("change", function onAnyChange(event) {
  // Runs for every field
})

ON("load-record", function onLoad() {
  ALERT("Welcome", "Review the details before editing.")
})
```

- Les bindings officiels identifient le champ par son `data_name` : les gestionnaires des événements
  de champ déclenchés par les bindings doivent donc eux aussi s'enregistrer avec le `data_name`. Le
  core compare la chaîne d'enregistrement à l'identique et ne convertit pas entre `key` et
  `data_name`.
- Omettez le champ pour exécuter le gestionnaire pour tous les champs.
- Un type d'événement inconnu affiche un avertissement, et le gestionnaire n'est pas enregistré.
- `ON` et `OFF` dans un gestionnaire prennent effet une fois le déclenchement réussi. Si le
  déclenchement est rejeté, ils n’ont aucun effet. Les callbacks imbriqués dans un gestionnaire
  fonctionnent sur Hermes, mais ils ne peuvent pas utiliser les variables locales du gestionnaire
  englobant.

## Comment s'exécute le code des gestionnaires

Le moteur conserve le code source de chaque gestionnaire défini dans `form.events.code` et exécute
ce code à chaque déclenchement de l'événement. Un gestionnaire ne peut donc pas utiliser les
variables du code qui l'entoure : les constantes, variables et fonctions déclarées au niveau
supérieur de `form.events.code` ne sont pas disponibles dans le gestionnaire.

```js
const ADULT_AGE = 18

ON("change", "age", function onAgeChange(event) {
  // Fails with "ADULT_AGE is not defined"
  if ($age >= ADULT_AGE) {
    SETVALUE("adult_note", "Adult")
  }
})
```

Dans un gestionnaire, lisez les valeurs du formulaire avec `$data_name`. Pour une logique partagée
par plusieurs gestionnaires, passez une fonction dans l'option `helpers` du moteur.

Les gestionnaires doivent être synchrones. Si un gestionnaire est `async` ou renvoie une promesse,
le moteur émet un avertissement, et `trigger()` ne renvoie que les opérations créées par le
gestionnaire avant son premier `await`. Les opérations créées ensuite sont abandonnées avec un
avertissement, et une erreur levée après un `await` est signalée au lieu d'échapper au moteur. Ces
avertissements s'affichent dans la console en développement et parviennent aux gestionnaires de
`WarningSystem` que vous avez enregistrés.

Comme le moteur conserve lui-même le code source, les gestionnaires s'exécutent aussi sur Hermes, le
moteur JavaScript de React Native, qui n'expose pas le code source des fonctions. Cela fonctionne
pour les déclarations de fonction, les expressions de fonction et les fonctions fléchées écrites
dans `form.events.code`, y compris celles affectées à une variable puis passées à `ON`.

Pour tout autre callback, le moteur lit le code source avec `toString()`. Cela concerne les
callbacks qui proviennent de `helpers`, les méthodes d'objet, les
getters et setters, et les membres de classe. Ce mécanisme fonctionne dans Node.js et dans les
navigateurs, mais pas sur Hermes. Dans ce cas, le moteur affiche
`Event callback source is unavailable` et exécute les autres gestionnaires.

## Quand les gestionnaires s'exécutent

Un gestionnaire ne s'exécute que lorsque son événement est déclenché, soit par un binding, soit par
votre application avec `engine.trigger(eventType, fieldDataName, metadata)`. Créer le moteur ou
exécuter `eval()` ne déclenche aucun événement.

Pour un même déclenchement, les gestionnaires enregistrés pour ce champ s'exécutent d'abord, dans
l'ordre de leur enregistrement. Les gestionnaires enregistrés pour tous les champs s'exécutent
ensuite. Si un gestionnaire lève une erreur, le moteur affiche `[form0] Expression evaluation failed`
dans la console et les autres gestionnaires s'exécutent quand même.

## Ce qu'un gestionnaire peut lire

Un gestionnaire lit les valeurs des champs avec `$data_name`, comme un calcul. Il voit les valeurs du
moment où l'événement a été déclenché. Pour un événement `change` venant d'un renderer officiel,
c'est après la passe d'évaluation qui a suivi la modification : les champs calculés sont donc déjà à
jour.

Les champs qu'un gestionnaire peut lire dépendent de l'événement :

- **Les événements d'enregistrement**, comme `load-record` et `edit-record`, ne peuvent lire que les
  champs du formulaire principal.
- **Les événements de champ**, comme `change`, suivent les mêmes règles qu'un calcul défini sur le
  champ qui les a déclenchés. Voir [Portées parent et enfant](/fr/core/engine/parent-child-scopes).

Chaque gestionnaire reçoit aussi un objet `event` avec `type`, `fieldKey` (le `data_name` du champ)
et `timestamp`, ainsi que les métadonnées éventuellement passées à `trigger()`. Les renderers
officiels ajoutent la nouvelle `value` et la définition `field` aux événements `change`.

Les gestionnaires peuvent utiliser les builtins d'expression partagés, comme `IF` et `CHOICEVALUE`,
en plus des builtins d'événement. Les builtins réservés aux calculs, comme `SETRESULT`, ne sont pas
disponibles.

<Callout type="info" title="SETVALUE ne met pas à jour ce que lit le gestionnaire">
  `SETVALUE` ne fait qu'enregistrer une opération. Pour le reste du gestionnaire, `$data_name`
  renvoie toujours la valeur du moment où l'événement a été déclenché. La nouvelle valeur est
  visible une fois l'opération appliquée.
</Callout>

## Opérations

`SETVALUE` et `ALERT` ajoutent chacun une opération à la liste renvoyée par `engine.trigger()` :

```js
// SETVALUE("adult_note", "Adult")
{ type: "FIELD_OPERATION", operation: "SETVALUE", params: { fieldDataName: "adult_note", valueToSet: "Adult" } }

// ALERT("Welcome", "Review the details before editing.")
{ type: "UI_OPERATION", operation: "ALERT", params: { title: "Welcome", message: "Review the details before editing." } }
```

Les opérations de tous les gestionnaires d'un même déclenchement sont renvoyées ensemble, dans
l'ordre d'exécution des gestionnaires.

### Les opérations sont vérifiées avant d'être renvoyées

Avant que `trigger()` ne renvoie son résultat, le moteur vérifie chaque `SETVALUE` par rapport à la
portée du gestionnaire. Si l’un d’eux cible un champ que le gestionnaire ne peut pas écrire, ou un
champ absent du schéma, le moteur signale un avertissement et `trigger()` ne renvoie aucune
opération pour cet événement. Chaque `SETVALUE` renvoyé par `trigger()` cible un champ que le
gestionnaire a le droit de modifier.

### Comment les bindings officiels appliquent les opérations

Par défaut, les renderers officiels :

- affichent chaque `ALERT` dans leur propre boîte de dialogue ; et
- écrivent la valeur de chaque `SETVALUE` dans le formulaire et exécutent une nouvelle passe
  d'évaluation.

<Callout type="caution" title="Les champs de choix acceptent des identifiants textuels">
  `SETVALUE` accepte un identifiant textuel pour un `SingleChoiceField` ou `BooleanField`, et un
  tableau d’identifiants textuels pour un `MultiChoiceField`. Si une valeur a une forme incorrecte,
  aucune opération de cet événement n’est appliquée, et le renderer journalise `Event failed.` dans
  la console. Consultez la [référence de `SETVALUE`](/fr/core/builtins/events/setvalue).
</Callout>

Les composants `FormRenderer` de React et React Native permettent à une application de traiter les
opérations autres que les alertes via `engineOptions.onOperations`. Chaque renderer présente les
opérations `ALERT` et transmet les autres opérations à votre callback.

```js
function onOperations(operations, meta, applyDefault) {
  // meta is { eventType, fieldKey, metadata }
  console.log(`${meta.eventType} returned ${operations.length} operations`)
  applyDefault(operations, meta)
}
```

Appelez `applyDefault` avec les opérations que le binding doit traiter comme d'habitude.

### Appliquer les opérations sans renderer

Si vous utilisez form0-core directement, appliquez vous-même la liste renvoyée. Pour `SETVALUE`,
appelez `engine.setValue(fieldDataName, valueToSet)`, qui accepte un identifiant textuel pour un
champ de choix et lance l’évaluation. Consultez
[Cycle d'évaluation](/fr/core/engine/evaluation-cycle).

## Pas de chaîne d'événements de modification

Appliquer un `SETVALUE` exécute une nouvelle passe d'évaluation, mais ne déclenche pas `change` pour
le champ défini. Un gestionnaire `change` pour `age` qui définit `adult_note` n'exécute pas les
gestionnaires `change` de `adult_note`.

Si la définition d'un champ doit aussi déclencher la logique d'un autre, placez les deux dans le
même gestionnaire, ou utilisez un `CalculatedField` quand la valeur peut être dérivée d'autres
champs.

## Obtenir des résultats détaillés

`engine.trigger()` renvoie seulement les opérations. Utilisez
`engine.triggerDetailed(eventType, fieldKey, metadata)` lorsque vous avez aussi besoin des messages
de validation et des échecs. Cette méthode est synchrone et renvoie trois tableaux :

```js
const { operations, validationIssues, issues } = engine.triggerDetailed("validate-record")
```

- `operations` : ce qu’il faut appliquer. Si un gestionnaire échoue, ce tableau est vide.
- `validationIssues` : les messages de `INVALID()`.
- `issues` : les échecs survenus pendant l’exécution des gestionnaires, chacun avec `code`,
  `message`, `eventType` et `instancePath`.

Aucune de ces méthodes n’évalue le formulaire, ne sauvegarde un enregistrement ni ne ferme un
éditeur.

### Exécuter les gestionnaires d’une ligne

Pour exécuter les gestionnaires d’une ligne sans renderer, passez `eventScope.instancePath` à la
création du moteur. Le chemin de l’enregistrement principal est `[]`. Chaque segment de ligne
comporte `repeatableKey`, `instanceId`, `index` et `identity`. Les chemins utilisent les clés du
schéma, et les écouteurs utilisent `data_name`. Une ligne sans identifiant utilise
`identity: "position"`. form0 vérifie le chemin par rapport au schéma, mais votre application doit
vérifier que la ligne existe toujours.

Un gestionnaire de ligne peut lire ses propres champs, ainsi que les champs des lignes parentes et
du formulaire principal fournis par votre application. `SETVALUE()` écrit uniquement dans la ligne
actuelle. Les lignes sœurs, les lignes enfants et les collections répétables sont hors de portée.
Les métadonnées ne peuvent pas remplacer les propriétés de l’événement lui-même, comme son type ou
sa portée.

### Ce que chaque type de gestionnaire peut faire

| Gestionnaires                            | Peuvent                    | Ne peuvent pas                                                       |
| ---------------------------------------- | -------------------------- | -------------------------------------------------------------------- |
| `validate-record`, `validate-repeatable` | Appeler `INVALID(message)` | Modifier des valeurs, afficher des alertes ou renvoyer des promesses |
| `cancel-record`, `cancel-repeatable`     | Lire des valeurs           | Modifier des valeurs, appeler `INVALID()` ou afficher des alertes    |
| `unload-record`, `unload-repeatable`     | Lire des valeurs           | Modifier des valeurs, appeler `INVALID()` ou afficher des alertes    |

`save-record` et `save-repeatable` s’exécutent avant une sauvegarde. Il n’existe pas d’événements de
schéma `saved-*`. Les applications gèrent la sauvegarde, les messages de réussite et la fermeture de
l’éditeur.

Les métadonnées d’un événement peuvent contenir des objets simples, des tableaux, des dates, des
valeurs simples et des références `File` ou `Blob`, qui conservent leurs métadonnées et leur
contenu. Les autres types d’objets sont rejetés. Les gestionnaires du schéma ne peuvent pas être
asynchrones.

Consultez le
[contrat d’événements maintenu](https://github.com/paqu-io/form0-core/blob/development/EVENT_CONTRACT.md)
pour connaître toutes les règles.

## Enregistrements en lecture seule

Chaque gestionnaire reçoit `event.mode`, qui vaut `"readonly"` ou `"edit"` pour l’enregistrement
dans lequel il s’exécute. Une ligne en lecture seule dans un enregistrement modifiable reçoit
`"readonly"`. Le mode est indépendant du fait que l’enregistrement soit nouveau, qu’il s’agisse d’un
brouillon, et du réglage `read_only` d’un champ. Les métadonnées et les gestionnaires ne peuvent pas
le modifier.

`load-record` s’exécute une fois à chaque ouverture d’un enregistrement, dans les deux modes. Un
enregistrement ouvert en modification exécute ensuite `new-record` ou `edit-record`. Passer de la
lecture seule à la modification exécute `edit-record` sans relancer `load-record`.

Dans un enregistrement en lecture seule, les gestionnaires peuvent lire des valeurs, afficher un
`ALERT` et ajouter ou retirer des écouteurs. Un `SETVALUE` rejette tout le lot, y compris les
alertes et les changements d’écouteurs, et l’enregistrement reste lisible. `triggerDetailed()` le
signale dans `issues`, et `trigger()` ne renvoie aucune opération et signale un avertissement.

Placez l’initialisation qui doit s’exécuter à chaque début de modification dans un gestionnaire de
`new-record` ou `edit-record`, pas dans `load-record`. Les helpers que votre application passe au
moteur peuvent avoir leurs propres effets de bord, que form0 ne peut pas annuler.
