## Section

```json
{
  "type": "Section",
  "key": "details",
  "data_name": "details",
  "label": "Details",
  "display": "inline",
  "description": null,
  "description_mode": null,
  "visible": true,
  "visible_conditions": null,
  "elements": []
}
```

Attributs supplémentaires :

- `display` : `inline` ou `drilldown`.
- `elements` : champs imbriqués.

## RepeatableSection

Une `RepeatableSection` permet à l’utilisateur d’ajouter autant de lignes qu’il le souhaite, comme
les lignes d’une commande. Chaque ligne contient ses propres valeurs pour le même ensemble de
champs. Dans l’enregistrement de sortie, chaque ligne devient un enregistrement enfant.

```json
{
  "type": "RepeatableSection",
  "key": "items",
  "data_name": "items",
  "label": "Items",
  "display": "drilldown",
  "description": null,
  "description_mode": null,
  "visible": true,
  "visible_conditions": null,
  "location_enabled": false,
  "location_required": false,
  "title_field": {
    "type": "TitleField",
    "key": "@title",
    "data_name": "title",
    "label": "Title",
    "display": "default",
    "enabled": true,
    "visible": true,
    "visible_conditions": null,
    "read_only": true,
    "read_only_conditions": null,
    "elements": ["item_name", "item_date"]
  },
  "elements": [
    {
      "type": "TextField",
      "key": "item_name",
      "data_name": "item_name",
      "label": "Item name"
    },
    {
      "type": "DateField",
      "key": "item_date",
      "data_name": "item_date",
      "label": "Item date"
    }
  ]
}
```

Attributs supplémentaires :

- `location_enabled` : active les données de localisation des lignes.
- `location_required` : exige des données de localisation pour les lignes.
- `title_field` : `TitleField` facultatif servant à déterminer le titre de chaque enregistrement enfant. Utilisez `null` si aucun
  titre de ligne n'est configuré.

Les sections répétables produisent un tableau d'enregistrements enfants dans la sortie. Le titre de ligne configuré est
stocké dans `@title` sur chaque enregistrement enfant. Si toutes les parties du titre sont vides, `@title` vaut `null` ; les renderers
peuvent afficher un libellé de position comme `Items 1`, mais cette valeur de repli n'est pas enregistrée.

Les références du titre sont limitées aux données des enregistrements enfants de la section répétable. Elles peuvent pointer vers des champs
situés dans des conteneurs `Section` imbriqués ordinaires, mais pas vers des champs extérieurs à la section répétable ni situés dans une
`RepeatableSection` imbriquée. Les types acceptés sont `TextField`, `NumericField`, `DateField`, `TimeField`,
`SingleChoiceField`, `MultiChoiceField`, `BooleanField` et `CalculatedField`. Les clés de champ ordonnées sont
recommandées, mais les références par `data_name` sont acceptées dans les schémas écrits à la main.

## BuildingPlanSection

Lorsqu'un sommet partagé change, les murs adjacents non modifiés conservent leur alignement.
Leur longueur peut s'adapter à la jonction. Une épingle protège aussi les extrémités de la portion.

Les pièces commencent par des rectangles. Déplacez un sommet pour modifier ses deux portions de mur
adjacentes, y compris les murs diagonaux et les sommets des pièces découpées ou avec décrochements.
Le déplacement d'un mur reste parallèle à son orientation initiale. Les murs diagonaux du périmètre
suivent la direction horizontale ou verticale initiale ; les murs adjacents gardent leur direction
et adaptent leur longueur aux nouvelles intersections. Les sommets suivent aussi un guide horizontal
ou vertical. Maintenez Alt pour un mouvement libre sur les deux axes, ou utilisez **Free drag** sur
Native. Les cloisons intérieures découpées gardent leur règle de déplacement perpendiculaire.
Choisissez **Pin / unpin**, puis un mur, pour fixer sa position pendant la session d'édition actuelle.
Les épingles sont des contrôles de l'éditeur, pas des réponses enregistrées. Les changements partagés
sont prévisualisés ensemble et utilisent les commandes habituelles Save, Cancel et Undo/Redo de
l'élément et de l'étage. L'alignement tient compte de l'épaisseur physique à différents niveaux de zoom.

```json
{
  "type": "BuildingPlanSection",
  "key": "building_plan",
  "data_name": "building_plan",
  "label": "Building plan",
  "description": null,
  "description_mode": null,
  "visible": true,
  "visible_conditions": null,
  "read_only": false,
  "read_only_conditions": null,
  "node_overrides": null
}
```

Attributs supplémentaires :

- `building_plan` : métadonnées de topologie et de liaison produites par le compilateur ; définir les questions avec `node_overrides`.
- `node_overrides` : surcharges appliquées aux nœuds générés.
- `elements` : RepeatableSections imbriquées et définitions de questions générées.

L'exemple ci-dessus est le schéma rédigé par l'auteur. L'expansion ajoute `elements` et
`building_plan` ; omettre ces deux attributs lors de la définition du champ. `elements` contient
la véritable hiérarchie de RepeatableSections générées. `building_plan` décrit son modèle, ses
clés générées et ses liaisons. Aucun ne stocke les pièces ou murs dessinés par l'utilisateur.
Ajouter les questions avec `node_overrides`, sans modifier l'arbre `elements` généré.

Les anciens `building_plan: { nodes: [], edges: [] }` et `elements: []` étaient des espaces réservés
redondants que l'expansion remplaçait. Ils ne définissaient pas la géométrie d'une réponse.

La géométrie est conservée dans des enregistrements enfants ordinaires. Les réponses de chaque
enregistrement sérialisé sont dans `form_values` ; les collections d'étages, de pièces et de murs
contiennent des enfants avec leur propre `form_values`. Les principaux champs générés sont :

| Propriétaire                       | Champ avant les suffixes générés | Contenu stocké                                                                          |
| ---------------------------------- | -------------------------------- | --------------------------------------------------------------------------------------- |
| Pièce                              | `room_vertices`                  | Texte JSON versionné avec sommets métriques du polygone et identifiants stables         |
| Mur physique appartenant à l'étage | `wall_geometry`                  | Texte JSON versionné avec segments de construction métriques                            |
| Ligne de face de mur d'une pièce   | `wall_face_model`                | Texte JSON versionné avec références au mur physique et portions liées                  |
| Étage, pièce, mur ou ouverture     | Champs `*_model` générés         | Identités stables et métadonnées de relations, valeurs par défaut et valeurs explicites |

Les clés réelles dépendent de l'expansion et du mode de clés choisi. Dimensions et positions des
ouvertures restent des réponses numériques ordinaires dans leurs enregistrements enfants du mur.
L'adaptateur reconstruit un instantané sémantique structuré ; aucun autre objet de géométrie dans
le schéma n'est nécessaire.

<Callout type="info" title="Contrat expérimental de BuildingPlan">
  Ce contrat est développé dans des versions coordonnées de core, CLI, React et Native. Les anciens
  enregistrements de développement ne sont pas migrés automatiquement. Aucun export IFC ou RDF n'est
  inclus.
</Callout>

Le canevas représente des enregistrements répétables ordinaires. Sélectionner un élément ouvre son
éditeur de ligne ; Add, Edit, Save, Cancel et Remove conservent leur rôle. Save dans un enfant accepte
les modifications dans le brouillon parent. Save dans un étage les accepte dans le formulaire ;
l'application reste responsable de la persistance. Annuler une pièce ou un mur rétablit aussi les
modifications de géométrie partagée initiées dans cet éditeur.

Les étages possèdent les murs physiques et les observations. Les pièces possèdent les portions de
face qui référencent ces murs ; portes et fenêtres appartiennent au mur physique. Poteaux, poutres
et objets génériques restent associés à la pièce. Deux pièces décalées peuvent ne partager que 2 m
d'un mur continu de 8 m. Sujets physiques, sommets, segments et portions ont des identifiants stables
distincts des identifiants de ligne et des clés du schéma. Les coordonnées sont métriques.

La hiérarchie d'édition reste étage → pièce → poteau/poutre/objet/mur → porte/fenêtre.
Les collections canoniques de murs physiques et d'observations de l'étage sont un stockage interne,
sans éditeur ni entrée de navigation distincts. Les questions physiques partagées apparaissent dans
la ligne de mur habituelle de la pièce. Un éditeur enfant Observations n'y apparaît que si des
questions d'observation sont explicitement configurées ; il est absent du parcours par défaut.

Les questions personnalisées de mur concernent par défaut le côté de la pièce. Utilisez
`node_overrides.walls.field_bindings` pour choisir une autre portée :

```js
field_bindings: {
  construction_material: { scope: 'physical_wall', inherit: true },
  surface_condition: { scope: 'room_face' },
  measured_moisture: { scope: 'observation' },
}
```

Ces noms correspondent aux questions ordinaires de `walls.extra_elements`, avec leurs attributs
habituels. Les réponses physiques sont évaluées dans le contexte du sujet physique. Les questions
de pièce peuvent lire les propriétés physiques déclarées. Un calcul physique ne doit pas dépendre
des réponses privées d'une pièce. Les observations ont une date, une couverture et des preuves
explicites ; les valeurs héritées ne créent jamais de mesures ni de preuves.

Les propriétés adaptées peuvent activer l'héritage dynamique, dont initialement l'épaisseur et la
hauteur de mur. L'ordre est : valeur explicite du segment ou du mur, une seule valeur explicite distincte des
pièces adjacentes, valeur de l'étage, valeur du schéma. Des valeurs identiques concordent ; des
valeurs différentes nécessitent une résolution commune au mur. La hauteur n'est jamais déduite de
celle de l'étage. Une valeur explicitement vide ou inconnue se distingue de l'héritage. Les libellés
indiquent l'origine ; réinitialiser rétablit l'héritage. Obligation et validation portent sur la valeur effective.

Les aperçus ne modifient pas l'état accepté. Un geste terminé valide une opération. Déplacer une
pièce détache ses côtés partagés et réconcilie ses connexions à destination. Modifier une face
partagée peut ajuster seulement l'étendue liée du voisin et créer un décrochement valide. La largeur
des ouvertures reste fixe lors des étirements ordinaires. Une géométrie invalide conserve la dernière
disposition valide et affiche un conflit. Undo et Redo restaurent des opérations complètes sans
rejouer les événements du cycle de vie. Les objets génériques restent gérés dans le formulaire.

Le canevas dessine la matière des murs à leur épaisseur effective, y compris les valeurs explicites
des segments, et affiche chaque ouverture une seule fois dans cette bande. Les lignes de face
restent les cibles de sélection et de modification. Les jonctions valides sont dessinées sans
traits internes doublés ; leur dessin ne fusionne ni identités ni réponses. Une épaisseur
explicitement inconnue apparaît comme une ligne schématique en pointillés, sans largeur inventée.
Ces formes sont calculées et ne sont pas stockées dans l'enregistrement. CLI privilégie la pièce
en cours de modification lorsque des portions se superposent ; React et Native limitent la
modification à la pièce active. La vue initiale inclut la matière extérieure près de l'origine ;
les gestes suivants ne la recentrent pas. Un changement d'épaisseur fixe la face de la pièce active,
ou la face de référence stable pour un changement à l'échelle de l'étage. Passer de 0,20 m à 0,30 m
maintient cette face et déplace l'autre de 0,10 m, sous réserve de validation. Des valeurs explicites
de pièce contradictoires exigent toujours une résolution commune au mur.

Lorsqu'un nouveau retour de décrochement rejoint un mur existant, un contact compatible partage
ce sujet physique. La face de la pièce active reste fixe et la face opposée est espacée de
l'épaisseur effective, sans bande doublée. Sa ligne de face peut donc porter le libellé du mur existant.
Le détachement d'une pièce réconcilie les étendues enregistrées du mur immobile avec ses faces
restantes, en conservant identité, positions des ouvertures et contexte des observations datées.
Les cloisons créées indépendamment et les longueurs nécessaires aux ouvertures conservées restent intactes.

Chaque portion droite de face possède sa ligne de mur habituelle. **Split** crée des portions
modifiables explicites d'un mur droit, en conservant son identité physique, ses ouvertures et ses
observations originales. Choisissez un point avec alignement magnétique ou une distance depuis
l'extrémité marquée `0`. La coupe reste
après réalignement et enregistrement/rechargement. **Rejoin** retire la coupe choisie lorsque ses
portions sont contiguës, colinéaires et portent des réponses compatibles. Un décalage ou des réponses
contradictoires affichent une explication ; une coupe traversant une ouverture est refusée. Chaque
commande est une opération réversible dans le brouillon habituel. React et Native les proposent
dans la pièce active ; sur Native, sélectionnez un mur en mode Select pour saisir la distance exacte.
La session accepte `split_face` (`faceId`, `offset` en mètres) et `rejoin_cut` (`cutId`). Les sommets
métriques gardent la référence `editingCutId` ; `split_wall` / `join_walls` restent des opérations
physiques distinctes.
Pour une portion explicitement divisée, l'unique champ **Thickness** existant modifie cette étendue
physique. Aucun champ d'épaisseur supplémentaire ni choix de portée n'est ajouté. Les faces
partagées affichent la même valeur ; le reste conserve son épaisseur effective. Les surcharges sont
enregistrées sur les segments de construction ; les valeurs par défaut restent actives et Reset
rétablit l'héritage. La face active reste fixe et la face opposée peut former un ressaut lors d'un
changement d'épaisseur. Rejoin conserve les divisions significatives. Les autres questions physiques
gardent leur portée déclarée. Les guides magnétiques utilisent aussi les bords fixes de la même
pièce et leurs prolongements, pour réaligner exactement les retours valides.
Les portions de cloisons intérieures se déplacent perpendiculairement à leur tracé initial, avec
des retours connectés. Utilisez Rejoin avant de déplacer ou remodeler toute la cloison. Enregistrez
ou annulez une entrée de mur ouverte avant de la supprimer avec Rejoin.

Un décrochement valide peut faire passer quatre lignes à six. Les nouveaux tracés indépendants
reçoivent des identités physiques distinctes par défaut ; le partage partiel seul ne divise pas
un mur continu. `editingPolicy: { preserveWallGrouping: true }`
conserve le regroupement physique pour les opérations futures, avec des lignes de face distinctes.
`separate_wall` sépare explicitement des segments (`wallId`, `segmentIds` facultatif). Ces choix ne
décrivent pas une rénovation et ne créent aucune preuve de mesure. Les identités et sources sont conservées.

L'alignement magnétique et le déplacement doux près des bords sont activés par défaut et réglables
séparément avec `editingPolicy.snapping` et `editingPolicy.edgeAutoPan`. Settings expose ces préférences
et le regroupement physique dans CLI ; React et Native proposent des commandes d'alignement et de
déplacement. Alt suspend l'alignement pendant un geste sur ordinateur. Les guides tiennent compte de
l'épaisseur et du zoom ; les prolongements fixes aident à supprimer les petits décrochements. Le
déplacement s'arrête au relâchement ou à l'annulation, sans zoom ni recentrage. Ces préférences ne
sont pas des réponses. Un rejet affiche un conseil de correction et conserve la géométrie acceptée.
Les diagnostics par périmètre restent disponibles dans l'API commune.

Les faces parallèles du même côté peuvent s'aligner sur une ligne et ses prolongements ; les
faces partagées opposées conservent l'écart d'épaisseur. Un déplacement peut aligner les deux axes.
Un contact compatible devient une géométrie partagée ; un alignement sans contact ne fusionne pas
les sujets physiques. Les murs rejoignent les angles redimensionnés et les jonctions tiennent
compte de l'épaisseur, y compris au retour à une ligne droite ou lors d'une inversion de retour.

Un angle coupant partiellement une porte ou une fenêtre exige une confirmation à la fin du geste.
Annuler conserve le plan accepté. Confirmer conserve la position proposée et supprime les ouvertures
physiques indiquées de toutes les vues ; la suppression d'observations associées est annoncée.
Géométrie et suppressions confirmées constituent une seule opération Undo/Redo. Une confirmation
périmée ne remplace pas de nouvelles réponses. Une ouverture entièrement hors de la face de la pièce
modifiée reste sur son mur physique. Les hôtes peuvent fournir `confirmOpeningRemoval` au contrôleur ;
le comportement par défaut refuse la suppression. Les écritures ordinaires renvoient le conflit
localisé sans supprimer silencieusement une ouverture.

Enregistrez ou annulez un éditeur ouvert pour une ouverture concernée avant de répéter le déplacement.

Les API portables sont exportées par `form0-core` et `form0-core/building-plan` :

| API                                                  | Rôle                                                                                       |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `createBuildingPlanSession`                          | Instantanés, aperçus, validation, points de contrôle, historique et diagnostics            |
| `readBuildingPlanRecord` / `writeBuildingPlanRecord` | Enregistrements canoniques et instantanés sémantiques versionnés                           |
| `createBuildingPlanRecordSession`                    | Écritures de ligne limitées et présentation des valeurs effectives                         |
| `createBuildingPlanEditor`                           | Cycle des éditeurs imbriqués existants et transactions partagées                           |
| `isBuildingPlanInternalCollection`                   | Filtre de présentation des collections canoniques et éditeurs d'observation non configurés |

Utilisez les métadonnées de `expandBuildingPlanSchema` pour résoudre les clés générées. Les champs
physiques et listes d'ouvertures affichés depuis une pièce sont des projections : la sérialisation
ordinaire omet ces copies et conserve une seule fois les enregistrements canoniques. Conservez les
champs d'identité et de géométrie lors du stockage et du rechargement. Panoramique, zoom, sélection
et gestes inachevés sont un état transitoire.

L'enregistrement brut est volumineux : les clés générées identifient les champs, et les champs de
géométrie/modèle contiennent du texte JSON échappé pour conserver le contrat habituel des valeurs.
Pour l'inspection ou le traitement applicatif, décodez l'enregistrement en objets sémantiques ordinaires :

```js
import {
  expandBuildingPlanSchema,
  buildFormRecordSnapshot,
  readBuildingPlanRecord,
} from "form0-core"

const expanded = expandBuildingPlanSchema(schema)
const runtime = buildFormRecordSnapshot(expanded.schema, savedRecord)
const plan = readBuildingPlanRecord({ meta: expanded.buildingPlanMeta[0], record: runtime })
// plan.floors[0].rooms[0].vertices
// plan.floors[0].walls[0].segments
```

Cette vue est reconstruite à la demande ; la soumission ne stocke pas une autre copie indépendante.
Les coordonnées sont des mètres locaux à l'étage, x vers la droite et y vers le bas. Chaque liaison
de face indique son mur/segment et l'intervalle de distance couvert le long du segment, ce qui rend
le partage partiel explicite.
