## Mode d’interaction

Définissez `mode="edit"` ou `mode="readonly"`. Les formulaires en lecture seule peuvent proposer un
bouton de passage en édition avec `allowReadOnlyEditToggle` ; utilisez
`readOnlyEditToggleDisabledReason` lorsque l’application host doit expliquer pourquoi l’édition
n’est pas disponible.

`showPrimaryActionsInViewMode` détermine si les actions principales désactivées restent visibles en
mode consultation.

## Mode d’ouverture des entrées répétables

`repeatableEntryMode` accepte `readonly` (par défaut) ou `edit` pour les lignes existantes à tous
les niveaux d’imbrication. Les lignes existantes s’ouvrent en consultation avec Edit si leur parent
permet la modification ; les nouvelles s’ouvrent en modification. Un parent en lecture seule permet
de consulter ses descendants, mais empêche leur modification, leur ajout et leur suppression.
L’option de modification directe ne contourne pas les restrictions du parent.

La consultation conserve les valeurs calculées acceptées sans exécuter les calculs ni appliquer
les valeurs par défaut manquantes. Les conditions et la validation intrinsèque utilisent ces
valeurs. Modifier évalue avec les valeurs actuelles des ancêtres autorisés. Avec des totaux acceptés
110/220 et une racine 330, consulter conserve 110/220 ; modifier la ligne 1 produit 120, l'enregistrer
donne 340 à la racine et annuler conserve 330. Après un échec de persistance, les valeurs
sélectionnées restent un travail non enregistré lors du retour en consultation.

L'ouverture gérée attend `load-record`/`load-repeatable`, puis l'événement new/edit correspondant
en modification directe. Consultation → Modification exécute edit sans répéter load. `event.mode`
vaut `readonly` ou `edit` pour l'enregistrement exécutant l'événement, indépendamment du mode du
parent. Consulter permet les lectures, ALERT et ON/OFF du périmètre ; une écriture rejette tout le
lot avant délégation au host. Déplacez l'initialisation qui écrit vers new/edit ou protégez les
setters de load pour la modification directe. La version coordonnée du core avec contrôle du mode
est requise ; la structure du schéma et de l'enregistrement sauvegardé reste identique.

## Emplacement

`formPlacement` accepte :

- `form-page` pour le contenu normal d’une page ;
- `form-modal` pour un affichage dans une modale ;
- `form-spotlight` pour un affichage dans un panneau latéral ou en mode spotlight.

Pour les overlays, fournissez `onRequestClose`. `autoCloseOverlayOnSubmit` ferme l’overlay après une
soumission synchrone réussie ou une fois la promesse de soumission renvoyée résolue. La confirmation
d’abandon tient compte des modifications du renderer et de `externalDirty`.

## Mise en page et navigation

- `labelPosition` accepte `top` ou `side`.
- `labelWidthPercent` contrôle la colonne des libellés dans la mise en page latérale.
- `formWidth` accepte une valeur de largeur CSS.
- `forceShowNavigationPanel` garde la navigation par sections visible alors qu’elle serait normalement réduite.
- `simplifiedMode` présente un champ à la fois ; `onSimplifiedNavigation` observe la progression.

Les sections, les entrées répétables, la navigation vers les erreurs de validation, la gestion du
focus et les actions au clavier sont gérées par `FormRenderer`. Gardez le comportement conditionnel
dans le schéma plutôt que de le dupliquer dans l’état React.
