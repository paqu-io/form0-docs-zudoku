Les renderers personnalisés modifient l’affichage sans sortir de `form0-core` les calculs, la
visibilité, le caractère obligatoire ni la validation.

## Surcharges ciblées

Privilégiez `FieldRegistryProvider` lorsqu’une application, une route, un test ou une story
Storybook a besoin d’un ensemble de renderers isolé :

```jsx
import { FieldRegistryProvider, FormRenderer } from "form0-react"
import { DateField } from "./date-field.jsx"

export function AppForm({ schema }) {
  return (
    <FieldRegistryProvider renderers={{ DateField }}>
      <FormRenderer schema={schema} />
    </FieldRegistryProvider>
  )
}
```

Un renderer reçoit le même contrat de champ que les renderers par défaut :

```jsx
function DateField({ field, value, onChange, readOnly, inputProps, className }) {
  return (
    <input
      {...inputProps}
      className={className}
      type="date"
      value={value ?? ""}
      disabled={readOnly}
      onChange={(event) => onChange(event.target.value)}
    />
  )
}
```

Conservez les propriétés d’accessibilité fournies dans `inputProps`.

## Instances de registre et surcharges globales

Utilisez `createFieldRegistry({ includeDefaults, renderers })` pour créer une instance de registre
explicite. Les fonctions de module `registerFieldComponent`, `unregisterFieldComponent` et
`resetFieldComponents` modifient le registre par défaut partagé : réservez-les de préférence à
l’amorçage de l’application ou aux tests.

Seuls les types de champs déclarés par `form0-core` peuvent être enregistrés. Un nouveau type de
champ de schéma doit d’abord être défini dans le noyau ; un renderer React seul ne peut pas étendre
le contrat du schéma.
