## Valeurs initiales et valeurs prioritaires

Utilisez `initialValues` pour l’enregistrement en cours de modification. `overrideValues` est
prioritaire et sert aux valeurs qui doivent l’emporter côté host, comme un statut fourni par
l’application.

Pour une restauration complète, privilégiez `initialSnapshot` :

```jsx
<FormRenderer
  engineOptions={{ events: { recordKind: "existing" } }}
  schema={schema}
  initialSnapshot={{
    raw_values: saved.raw_values,
    repeatable: saved.repeatable,
    timestamps: saved.timestamps,
  }}
  onSnapshotChange={(snapshot, change) => {
    if (change.dirty) queueDraft(snapshot)
  }}
  onSubmit={saveRecord}
/>
```

Un snapshot initial remplace `initialValues` pour les valeurs brutes des champs. Il restaure aussi
les entrées répétables imbriquées et les horodatages client et serveur comme un état cohérent.

## Échecs d’enregistrement et messages de console

Si le callback `onSubmit` échoue, un rapport est écrit par défaut dans `console.error`, avec l’étape
de l’échec et l’erreur d’origine. Le rejet du callback de persistance conserve les modifications pour
une nouvelle tentative et ne confirme pas un enregistrement réussi. Affichez un message utile dans
votre application et relancez l’erreur ; terminer normalement ou intercepter sans relancer signifie
que l’enregistrement a réussi.

`submissionDiagnostics` contrôle ces messages de console :

```jsx
<FormRenderer
  schema={schema}
  engineOptions={{ events: { recordKind: "new" } }}
  submissionDiagnostics={{ saveFailures: true, validationBlocks: false }}
  onSubmit={saveRecord}
/>
```

- `saveFailures` vaut `true` par défaut. Utilisez `false` si votre application signale déjà les échecs.
- `validationBlocks` vaut `false` par défaut. Utilisez `true` pour journaliser les tentatives bloquées
  de Submit et de Save dans les lignes répétables. Un champ obligatoire vide bloque la validation ;
  ce n’est pas une exception d’enregistrement.

Ces réglages restent à jour, même pendant un enregistrement en cours. Ils sont indépendants de
`debug`, de `engineOptions.diagnostics.console` et du cycle de vie. Les rapports n’ajoutent ni valeurs
du formulaire, ni snapshots, ni chemins d’enregistrements. Les échecs de préparation incluent les
codes et messages des problèmes. Annuler une confirmation reste silencieux ; une exception du
callback est signalée comme un échec du callback. Les messages existants du noyau conservent leur
propre comportement.

Essayez avec un champ obligatoire : cliquez sur Submit avec ce champ vide. Son message de validation
apparaît et la console reste silencieuse. Activez `validationBlocks` et cliquez à nouveau sur Submit :
une ligne de blocage par validation apparaît. Remplissez le champ, modifiez temporairement `saveRecord` pour qu’il lance
`new Error("Example save failure")`, puis cliquez sur Submit : un rapport d’échec
apparaît et les valeurs modifiées restent disponibles pour réessayer.

Ces contrôles concernent les actions intégrées du renderer. Une application qui appelle directement
`prepareSave()` reste responsable de l’inspection et du signalement du résultat renvoyé.

## Observer les brouillons

`onSnapshotChange(snapshot, change)` est d’abord appelé avec `{ kind: "seed", dirty: false }`. Les
modifications ultérieures de l’utilisateur utilisent `{ kind: "change", dirty: boolean }`.

Le snapshot contient :

```js
{
  raw_values: {},
  repeatable: {},
  timestamps: {
    created_at_client: null,
    updated_at_client: null,
    created_at_server: null,
    updated_at_server: null,
  },
}
```

## Soumettre des enregistrements

`onSubmit(record, meta)` reçoit l’enregistrement structuré décrit dans
[Sortie et enregistrements](/fr/core/output-records). `meta` contient `rawValues`, `repeatable`,
`timestamps` et `validationSummary`.

Si `onSubmit` renvoie une promesse, un overlay configuré avec `autoCloseOverlayOnSubmit` ne se ferme
qu’une fois la promesse résolue. En cas de rejet, il reste ouvert. Utilisez `submitBlockedReason`
pour les exigences de l’application extérieures au schéma et `externalDirty` pour l’état de
l’application extérieur au renderer.

## API des événements gérés

Voir le contrôleur et le contrat des périmètres dans [FormRenderer](/fr/bindings/react/form-renderer).

`engineOptions.events`: `lifecycle` (true), `recordKind` obligatoire (new/existing), `fieldInteractions` ([focus, blur, click]). Utilisez `lifecycle: false` pour le cycle historique ou `fieldInteractions: []` pour désactiver les interactions automatiques.
`engineOptions.onEventController(controller | null)`: `dispatch(request)`, `prepareSave(request)`.

La préparation ne persiste ni ne ferme. Les brouillons racine conservent les constats dans le résumé ; submit et l’acceptation des lignes sont bloqués par une validation invalide. Les diagnostics de calcul restent indépendants. Aucune évaluation ou agrégation des lignes fermées.

## Révision des calculs enfants et persistance

L’envoi ordinaire actualise automatiquement les calculs enfants fermés si le réglage est omis.
`form.repeatable_recalculation: 'confirm'` exige une révision. Le host peut l’exiger avec
`mode: 'confirm'`, mais `automatic` ne peut pas réduire cette exigence du formulaire. `allowRetain`
est une permission explicite et n’active pas la confirmation à lui seul. Le choix concerne tous les
enfants affectés ou aucun. La préparation racine est refusée tant qu’un éditeur enfant reste non accepté.

La révision affiche titres/chemins, libellés, anciennes/nouvelles valeurs et compteurs par pages
bornées. Personnalisez les textes avec `submissionOptions.messages`. Tous les résultats de validation
restent disponibles avec leur chemin ; l’interface les pagine et mène à l’enregistrement ou au champ.
Les résultats personnalisés de portée appartiennent à l’enregistrement, sans champ inventé.

```jsx
<FormRenderer
  engineOptions={{ events: { recordKind: "existing" } }}
  schema={schema}
  initialSnapshot={savedSnapshot}
  initialFreshness={savedFreshness}
  submissionOptions={{ mode: "confirm", allowRetain: true }}
  onSubmit={async (record, meta) => {
    await storage.save({ record, freshness: meta.freshness })
  }}
/>
```

La réussite du callback reconnaît la persistance. Enregistrez ensemble l’enregistrement sélectionné et
son compagnon de fraîcheur avant de résoudre ; le callback doit lever une erreur ou rejeter en cas
d’échec ou d’annulation. Choisir `20 → 24` conserve `24` comme travail non enregistré si la validation
ou la persistance échoue ensuite. La fraîcheur reste hors des valeurs enregistrées. Restaurez-la avec
`initialFreshness` ; une ancienne reconnaissance ne supprime pas un état en attente plus récent.
Des totaux conservés `[110,220]` donnent `330`, jamais le `360` de la proposition actualisée.

Les contrôleurs de préparation n’ouvrent pas de dialogue et ne persistent rien. Vérifiez `eligible`,
gérez `requires_decision` avec `payload: null` et reconnaissez uniquement le `preparationId` enregistré.
Les pages comportent 50 changements par défaut, 100 au maximum. Continuez avec `prepareSave()` et
`decision: { reviewId, action: 'refresh' | 'retain' | 'cancel' }`. Des entrées/configurations modifiées
ou une nouvelle préparation invalident la révision. La validation précède le hook de sauvegarde,
exécuté une fois ; ses écritures peuvent exiger une autre révision sans répéter le hook.

```js
const prepared = await controller.prepareSave({ intent: "submit", signal })
if (prepared.status === "requires_decision") {
  const page = await controller.getSaveChanges({
    preparationId: prepared.preparationId,
    offset: 0,
    limit: 50,
  })
  showReview(prepared, page)
} else if (prepared.eligible) {
  await storage.save({ record: prepared.payload, freshness: prepared.meta.freshness })
  controller.acknowledgeSave({ preparationId: prepared.preparationId })
}
```

Les workers conservent les révisions et rapports en interne. Les réponses usuelles contiennent les données sélectionnées et résumés ; les détails sont demandés par pages bornées. Les helpers de type fonction restent interdits dans les workers. Signaux et callbacks ne passent pas dans les messages à clonage structuré.

Les setters programmatiques utilisent le contrat strict partagé. Les valeurs initiales et remplacements du host restent des voies de chargement tolérantes, y compris en vue ; celle-ci conserve les calculs acceptés. [Voir le contrat de mise à jour des valeurs](/fr/core/engine/value-updates).
