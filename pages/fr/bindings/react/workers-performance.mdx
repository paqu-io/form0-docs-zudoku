## Exécution du moteur

La valeur par défaut, `engineMode="main-thread"`, évalue le moteur du formulaire sur le thread de
l’interface. Utilisez `engineMode="worker"` pour déplacer l’évaluation du moteur dans le module
worker fourni avec le paquet lorsque les Web Workers sont disponibles :

```jsx
<FormRenderer schema={schema} engineMode="worker" />
```

Vite prend en charge le modèle de module worker statique utilisé par le paquet et génère le worker
lors du build de production. Le starter Vite maintenu exclut `form0-react` de l’optimisation des
dépendances afin que ce worker reste disponible.

L’API publique de `FormRenderer` n’accepte ni URL de worker personnalisée ni fabrique de workers.
Les applications qui utilisent un autre bundler doivent vérifier qu’il prend en charge
`new Worker(new URL("./worker.js", import.meta.url), { type: "module" })` ; sinon, utilisez le mode
par défaut sur le thread principal.

Si le navigateur ne prend pas en charge les Workers, le binding revient à une exécution sur le
thread principal.

## Mode de stockage React

`engineStoreMode="snapshot"` clone le snapshot du moteur dans l’état React ; c’est la valeur par
défaut. `engineStoreMode="selector"` utilise des abonnements par champ pour limiter les nouveaux
rendus globaux.

Considérez le mode selector comme une optimisation : avant de l’adopter, vérifiez dans l’application
cible les erreurs des champs, les résumés de navigation, les sections répétables et le comportement
de la soumission.

## Options du moteur en mode worker

Les callbacks applicatifs (`onDiagnostics`, `onWarning`, `onUpdate`, `onOperations`) restent sur le host ; ils ne sont pas sérialisés dans le worker. Schéma, valeurs et configuration doivent accepter le clonage structuré. Les helpers contenant des fonctions et les autres configurations non clonables sont rejetés par une erreur claire avant tout envoi : utilisez `engineMode="main-thread"` pour les helpers fonctionnels. Un échec de configuration ne change pas le mode demandé et ne supprime pas silencieusement les helpers. Le repli existant lorsque Worker est indisponible reste inchangé. Les messages de diagnostic sont acceptés une fois par portée et évaluation actives ; les générations obsolètes ne restaurent pas les anciens résultats. Voir [FormRenderer](/bindings/react/form-renderer) pour l’interface commune.

Si vous remplacez le schéma ou les valeurs initiales pendant l’initialisation du worker, remontez `FormRenderer` pour initialiser le remplacement de façon prévisible. La protection existante contre les initialisations simultanées est conservée : les portées de diagnostic obsolètes se terminent immédiatement, sans programmer d’évaluation supplémentaire. Une collection active vide ne prouve pas que le remplacement a été évalué.

## Événements gérés et validation personnalisée

Les demandes/résultats gérés sont des données clonables. Callbacks et alertes restent côté host ; chaque réponse est consommée une fois et les anciennes générations sont rejetées. La promesse attend la délégation et les mises à jour par défaut du worker. Les helpers fonctions restent incompatibles avec worker ; utilisez main-thread. Validation et notifications n’ajoutent aucune évaluation.
