## État initial et restauration

Utilisez `initialValues` pour initialiser un enregistrement de façon ordinaire. `overrideValues` est
prioritaire et sert aux valeurs que contrôle votre application. Pour une restauration complète,
privilégiez `initialSnapshot` :

```jsx
<FormRenderer
  engineOptions={{ events: { recordKind: "existing" } }}
  schema={schema}
  initialSnapshot={savedDraft}
  onSnapshotChange={(snapshot, change) => {
    if (change.dirty) queueLocalDraft(snapshot)
  }}
  onSubmit={uploadRecord}
/>
```

Le snapshot regroupe les valeurs brutes, les entrées répétables imbriquées et les horodatages :

```js
{
  raw_values: {},
  repeatable: {},
  timestamps: {
    created_at_client: null,
    updated_at_client: null,
    created_at_server: null,
    updated_at_server: null,
  },
}
```

`onSnapshotChange(snapshot, meta)` signale d’abord `{ kind: "seed", dirty: false }` ; les
modifications ultérieures de l’utilisateur utilisent `{ kind: "change", dirty }`.

## Échecs d’enregistrement et messages de console

Lorsqu’un enregistrement échoue, `FormRenderer` conserve les valeurs de l’utilisateur pour qu’il
puisse réessayer et écrit un rapport dans `console.error` avec l’étape de l’échec et l’erreur
d’origine. Il n’affiche aucun message à l’utilisateur : faites-le dans votre application, puis
relancez l’erreur :

```jsx
async function handleSubmit(record) {
  try {
    await saveRecord(record)
  } catch (error) {
    setMessage("The record was not saved. Try again.")
    throw error
  }
}
```

Si vous interceptez l’erreur sans la relancer, `FormRenderer` considère que l’enregistrement a
réussi.

`submissionDiagnostics` contrôle ces messages de console :

```jsx
<FormRenderer
  schema={schema}
  engineOptions={{ events: { recordKind: "new" } }}
  submissionDiagnostics={{ saveFailures: true, validationBlocks: false }}
  onSubmit={handleSubmit}
/>
```

- `saveFailures` est actif par défaut. Réglez-le sur `false` si votre application signale déjà les
  échecs.
- `validationBlocks` est désactivé par défaut. Réglez-le sur `true` pour journaliser une ligne
  chaque fois que la validation bloque **Submit** ou **Save** sur une ligne répétable.

Un champ obligatoire vide est un blocage de validation, pas un échec d’enregistrement.

### Essayez

1. Appuyez sur **Submit** avec un champ obligatoire vide. Le champ affiche son message de validation
   et la console reste silencieuse.
2. Ajoutez `validationBlocks: true` et appuyez à nouveau sur **Submit**. La console affiche
   `[form0-react-native] Submit blocked by validation.`
3. Remplissez le champ, faites en sorte que `saveRecord` lève `new Error("Example save failure")` et
   appuyez sur **Submit**. La console affiche `[form0-react-native] Submit failed during onSubmit.`
   avec votre erreur, et les valeurs restent dans le formulaire.
4. Retirez le `throw` et appuyez à nouveau sur **Submit**. L’enregistrement réussit.

### Détails

- Ces réglages s’appliquent immédiatement, même pendant un enregistrement en cours. Ils sont
  indépendants de `debug`, de `engineOptions.diagnostics.console` et des réglages du cycle de vie.
- Les rapports n’incluent ni valeurs du formulaire, ni snapshots, ni chemins d’enregistrements. Les
  échecs de préparation incluent leurs codes et messages.
- Annuler une confirmation n’écrit rien dans la console. Une exception levée par votre callback est
  signalée comme un échec du callback.
- `form0-core` écrit ses propres lignes, comme `[EVENT HANDLER] Registered`. Ces réglages ne les
  contrôlent pas.
- Ces réglages couvrent les actions intégrées du renderer. Si vous appelez directement
  `prepareSave()`, examinez le résultat renvoyé.
- Les mêmes réglages s’appliquent aux échecs de `onSave` pour les brouillons. Les brouillons
  invalides restent enregistrables, et un brouillon enregistré avec succès ne journalise aucun
  blocage de validation.

## Enregistrer des brouillons ou soumettre des enregistrements

Définissez `primaryActionMode="save"` et fournissez `onSave(snapshot, meta)` pour une action
d’enregistrement de brouillon qui ne dépend pas de la validation. `meta` contient le résumé de
validation actuel et l’état de modification.

L’action de soumission par défaut valide d’abord le formulaire. `onSubmit(record, meta)` reçoit
l’enregistrement structuré décrit dans [Sortie et enregistrements](/fr/core/output-records), ainsi
que les valeurs brutes, l’état des sections répétables, les horodatages et le résumé de validation.

Le binding ne persiste ni ne synchronise aucune de ces deux données. Stockez les snapshots
localement, envoyez les enregistrements, relancez les échecs et résolvez les conflits dans votre application.

## Utiliser les événements depuis votre code

`engineOptions.events` définit les événements exécutés, et `engineOptions.onEventController` vous
donne un contrôleur pour vos propres boutons.
[FormRenderer](/fr/bindings/react-native/form-renderer) décrit les deux en détail.

| Option                     | Par défaut                   | Rôle                                                                            |
| -------------------------- | ---------------------------- | ------------------------------------------------------------------------------- |
| `events.recordKind`        | Obligatoire                  | `"new"` / `"existing"`.                                                         |
| `events.lifecycle`         | `true`                       | Définissez `false` pour ne garder que `load-record`, `edit-record` et `change`. |
| `events.fieldInteractions` | `["focus", "blur", "click"]` | Définissez `[]` pour désactiver les interactions automatiques.                  |

`onEventController(controller | null)` vous donne `dispatch(request)` et `prepareSave(request)`.

`prepareSave()` ne sauvegarde et ne ferme jamais rien. Le résumé renvoyé liste les messages de
validation d’un brouillon de l’enregistrement principal. Les échecs de validation bloquent une
soumission normale et l’acceptation d’une ligne, et les diagnostics de calcul ne bloquent rien.

## Examiner les lignes recalculées

Lorsqu’un utilisateur soumet le formulaire, `FormRenderer` recalcule automatiquement les lignes
sauvegardées. Définissez `form.repeatable_recalculation` sur `"confirm"` dans le schéma lorsque les
utilisateurs doivent d’abord examiner les valeurs modifiées.

`submissionOptions` modifie ce comportement depuis votre code :

- `mode: "confirm"` exige une revue même si le schéma ne le fait pas. `"automatic"` ne peut pas
  désactiver une confirmation définie dans le schéma.
- `allowRetain: true` permet à l’utilisateur de conserver d’anciennes valeurs. Cela n’active pas de
  revue à soi seul.
- `messages` remplace les textes de revue et de statut.

La revue par défaut affiche par pages les titres et chemins des lignes, les libellés des champs, les
anciennes et nouvelles valeurs et les totaux. Un choix s’applique à toutes les lignes modifiées ou à
aucune. Une sauvegarde est rejetée tant qu’un éditeur de ligne reste ouvert.

Tous les constats de validation restent disponibles avec leurs chemins d’enregistrement, et le
formulaire les pagine et renvoie vers l’enregistrement ou le champ. Un message de `INVALID()`
concerne son enregistrement, pas un champ.

### Sauvegarder l’enregistrement et son `freshness`

```jsx
<FormRenderer
  engineOptions={{ events: { recordKind: "existing" } }}
  schema={schema}
  initialSnapshot={savedSnapshot}
  initialFreshness={savedFreshness}
  submissionOptions={{ mode: "confirm", allowRetain: true }}
  onSubmit={async (record, meta) => {
    await storage.save({ record, freshness: meta.freshness })
  }}
/>
```

Lorsque votre callback se termine, form0 considère que la sauvegarde a réussi. Sauvegardez
l’enregistrement et `meta.freshness` ensemble avant sa résolution, et levez une erreur ou rejetez la
promesse en cas d’échec ou d’annulation.

`freshness` reste en dehors des valeurs du formulaire. Repassez celui qui est sauvegardé via
`initialFreshness`. Un accusé de réception plus ancien ne peut pas effacer un état en attente plus
récent. Si un utilisateur conserve d’anciens totaux de ligne `[110,220]`, la somme soumise est
`330`, jamais les `360` de la proposition actualisée. Si l’utilisateur change une valeur de `20` à
`24`, `24` reste un travail non sauvegardé même si la validation ou la sauvegarde échoue ensuite.

### Lancer une revue depuis votre interface

Un contrôleur prépare une sauvegarde sans ouvrir de boîte de dialogue ni rien sauvegarder :

```js
const prepared = await controller.prepareSave({ intent: "submit", signal })
if (prepared.status === "requires_decision") {
  const page = await controller.getSaveChanges({
    preparationId: prepared.preparationId,
    offset: 0,
    limit: 50,
  })
  showReview(prepared, page)
} else if (prepared.eligible) {
  await storage.save({ record: prepared.payload, freshness: prepared.meta.freshness })
  controller.acknowledgeSave({ preparationId: prepared.preparationId })
}
```

Vérifiez `eligible`, gérez `requires_decision`, où `payload` vaut `null`, et n’accusez réception que
du `preparationId` que vous avez sauvegardé. `getSaveChanges()` renvoie 50 entrées par défaut et 100
au maximum. Pour poursuivre une revue, appelez `prepareSave()` avec
`decision: { reviewId, action: "refresh" | "retain" | "cancel" }`. Modifier les entrées ou la
configuration, ou lancer une préparation plus récente, met fin à la revue.

La validation s’exécute avant le gestionnaire de sauvegarde, qui s’exécute une fois par tentative.
Si le gestionnaire modifie des valeurs, une nouvelle revue peut être nécessaire, mais il ne
s’exécute pas de nouveau.

`prepareSave({ intent: "draft" })` et l’action de sauvegarde du brouillon conservent les valeurs
calculées des lignes sauvegardées sans boîte de dialogue. Les échecs de validation sont signalés et
autorisent quand même un brouillon de l’enregistrement principal, mais l’échec d’un gestionnaire
l’empêche. Dans `onSave`, sauvegardez aussi l’enregistrement et `freshness` ensemble. Une écriture
hors ligne réussie est indépendante de la synchronisation ultérieure avec le serveur.

Les setters suivent les [règles de valeurs](/fr/core/engine/value-updates). `initialValues` et
`overrideValues` sont plus tolérants, y compris en lecture seule, où les valeurs calculées restent
telles qu’elles sont fournies.

## Valeurs masquées

Un champ avec
[`visible_preserve_value: false`](/fr/core/fields/common-attributes#effacer-une-valeur-lorsquun-champ-est-masqué)
est effacé pendant que l’utilisateur modifie le formulaire, y compris dans les lignes fermées. Il
reste effacé dans `raw_values`, `repeatable` et l’enregistrement soumis. Les autres champs
conservent leurs valeurs lorsqu’ils sont masqués, et un formulaire en lecture seule n’efface rien.

Pour vérifier les valeurs masquées conservées lors de la soumission finale, définissez
`validateHiddenValues` :

```jsx
<FormRenderer
  engineOptions={{ events: { recordKind: "existing" } }}
  schema={schema}
  submissionOptions={{ validateHiddenValues: true }}
  onSubmit={saveRecord}
/>
```

Une valeur masquée qui ne respecte pas ses propres règles bloque alors **Submit**. L’utilisateur ne
peut la corriger qu’en rendant le champ de nouveau visible. Utilisez cette option lorsque les
utilisateurs peuvent le faire. Sinon,
[vérifiez les valeurs masquées sur votre serveur](/fr/core/schema/validation#vérifier-les-valeurs-masquées-sur-un-serveur).
Les brouillons et les champs obligatoires masqués et vides ne sont pas concernés.
