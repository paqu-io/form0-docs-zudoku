`FormRenderer` valide et prépare un schéma, crée le moteur du formulaire, affiche les champs et les
sections natifs, et produit des enregistrements structurés ou des snapshots restaurables.

```jsx
<FormRenderer
  engineOptions={{ events: { recordKind: "new" } }}
  schema={schema}
  initialValues={{ name: "Ada" }}
  mode="edit"
  colorMode="light"
  labelPosition="top"
  onSubmit={saveRecord}
/>
```

## Propriétés essentielles

| Propriété               | Rôle                                                                                                                      |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `schema`                | Un schéma form0 contenant `form.elements`.                                                                                |
| `initialValues`         | Valeurs initiales des champs non répétables.                                                                              |
| `initialSnapshot`       | Restaure ensemble les valeurs brutes, l’état des sections répétables et les horodatages.                                  |
| `overrideValues`        | Applique des valeurs prioritaires sur les valeurs initiales.                                                              |
| `onSubmit`              | Reçoit l’enregistrement structuré et ses métadonnées, uniquement si la validation réussit.                                |
| `submissionDiagnostics` | Contrôle les rapports d’échec d’enregistrement (activés) et les blocages de validation (désactivés).                      |
| `submissionOptions`     | Définit les options de revue, les messages et `validateHiddenValues`.                                                     |
| `initialFreshness`      | Restaure le `freshness` sauvegardé d’un enregistrement.                                                                   |
| `eventDiagnostics`      | Contrôle les rapports d’événements en échec (activés).                                                                    |
| `onSave`                | Reçoit un snapshot sans exiger que le formulaire soit valide.                                                             |
| `onSnapshotChange`      | Observe les snapshots d’initialisation et de modification par l’utilisateur.                                              |
| `mode`                  | Démarre en mode `edit` ou `readonly`.                                                                                     |
| `repeatableEntryMode`   | Ouverture des lignes répétables existantes : `readonly` (par défaut) ou `edit` ; les nouvelles s’ouvrent en modification. |

## Intégration avec votre application

- `onRequestClose` active l’action d’annulation racine et reçoit `{ reason: "cancel" }` après
  l’éventuelle confirmation d’abandon.
- `headerAccessory` affiche du contenu de l’application juste sous l’en-tête intégré.
- `showHeader` masque l’en-tête intégré lorsque votre application fournit la navigation et les
  actions qui l’entourent.
- `primaryActionMode`, `primaryActionLabel` et `showPrimaryActionsInViewMode` personnalisent
  l’action principale intégrée.
- `onSchemaReady` reçoit le schéma préparé une fois les clés stables garanties.
- `engineOptions` fournit les helpers du noyau, la configuration de sécurité, les avertissements, la
  gestion des opérations et l’observation des mises à jour.

Les gestionnaires d’événements du schéma s’exécutent sur Hermes lorsqu’ils sont écrits sous forme
de fonctions ou de fonctions fléchées dans `form.events.code`. Consultez
[Comment s’exécute le code des gestionnaires](/fr/core/engine/events-operations#comment-sexécute-le-code-des-gestionnaires).

Poursuivez avec
[Valeurs, snapshots et soumission](/fr/bindings/react-native/values-snapshots-submission) ou
[Modes et navigation](/fr/bindings/react-native/modes-navigation).

## Options du moteur et diagnostics de calcul

`engineOptions` transmet les helpers, les réglages de sécurité, `onWarning`, `onUpdate`,
`onOperations` et les réglages de diagnostic de calcul au moteur principal et aux moteurs de ligne.
Les helpers et la sécurité sont définis à la création du moteur : remontez donc `FormRenderer` pour
les modifier. Les callbacks et le réglage de console sont mis à jour dans les éditeurs ouverts sans
nouvelle évaluation.

```jsx
const findingsByScope = new Map()

;<FormRenderer
  schema={schema}
  engineOptions={{
    events: { recordKind: "new" },
    diagnostics: { console: false },
    onDiagnostics(snapshot, meta) {
      if (meta.kind === "scope-ended") findingsByScope.delete(meta.scopeId)
      else findingsByScope.set(meta.scopeId, { snapshot, meta })
    },
  }}
/>
```

Les rapports de console sont activés par défaut. `diagnostics.console: false` désactive dans la
console les détails de calcul et les messages de rétablissement et de fin de portée, tandis que la
collecte et les callbacks continuent. Ajouter `onDiagnostics` ne désactive pas les rapports de
console. Les titres de la console sont en anglais.

`onDiagnostics(snapshot, meta)` reçoit une copie des constats après chaque évaluation terminée, y
compris la première, les constats répétés et `[]` après un rétablissement. La console ignore les
répétitions identiques et signale les constats nouveaux ou modifiés, le rétablissement et les
problèmes qui reviennent. Une erreur dans votre callback, y compris une promesse rejetée, ne peut
pas interrompre l’évaluation.

`meta` contient `scopeId`, `instancePath`, `evaluationId` et `kind`. Une portée correspond à la
durée de vie d’un moteur, et les identifiants d’évaluation y augmentent. Le chemin de
l’enregistrement principal est `[]`. Chaque segment de ligne comporte `repeatableKey`, `instanceId`,
un `index` commençant à zéro et `identity: "id" | "position"`. form0 utilise le `id` ou le
`record_id` d’une ligne, sinon sa position. Les constats portent le même chemin dans
`context.instancePath`. Les rapports ne créent jamais d’identifiants d’enregistrement.

Fermer ou supprimer un éditeur, remplacer son moteur ou son schéma, ou le démonter met fin à la
portée avec `onDiagnostics([], { ...meta, kind: "scope-ended" })`. Cela signifie que la portée n’est
plus observée, pas que la ligne s’est rétablie. Seuls les moteurs qui évaluent sont signalés : ce
callback n’est donc pas un rapport d’état complet et il ne réévalue pas les lignes fermées.

Les diagnostics de calcul restent en dehors de `state.errors`, des snapshots sauvegardés et des
enregistrements. Ils ne modifient ni la validation, ni la soumission, ni la sauvegarde des
brouillons, et n’ajoutent ni alertes ni panneaux.

### Gérer les opérations et les avertissements

`onOperations(operations, meta, applyDefault)` reçoit toutes les opérations sauf les alertes. Passez
celles que vous voulez traiter normalement à `applyDefault(selected, meta)`. Sans ce callback, le
traitement par défaut s’applique. Le renderer affiche chaque `ALERT` une fois. Votre callback doit
traiter chaque lot qu’il reçoit.

`onWarning` reçoit les avertissements du moteur, qui peuvent être limités, et ne remplace pas
`onDiagnostics`. `onUpdate(state, engine)` reçoit l’état et un objet moteur dont le type dépend de
la façon dont le formulaire s’exécute. Si vous n’avez besoin que des diagnostics, utilisez
`onDiagnostics`.

## Événements et validation personnalisée

Les événements de cycle de vie et les interactions de champ sont activés par défaut. Utilisez
`recordKind` pour indiquer si le formulaire contient un enregistrement nouveau ou existant :

```jsx
<FormRenderer
  schema={schema}
  engineOptions={{
    events: { recordKind: "existing" },
    onEventController: (controller) => {
      controllerRef.current = controller
    },
  }}
/>
```

`recordKind` doit valoir `new` ou `existing`, sauf si vous définissez `lifecycle: false`. form0 ne
le déduit pas des valeurs. Ces réglages durent toute la vie de l’éditeur : remontez-le donc pour
modifier `recordKind`, `lifecycle`, les helpers ou la sécurité. Les callbacks restent actifs.

- Un formulaire en lecture seule exécute `load-record`. Un formulaire en modification exécute
  `load-record`, puis `new-record` ou `edit-record`.
- Les lignes ouvertes utilisent les événements répétables, selon qu’elles sont nouvelles ou
  existantes.
- `lifecycle: false` ne garde que `load-record`, `edit-record` et `change` pour l’enregistrement
  principal. `fieldInteractions: []` désactive les interactions automatiques.
- Les champs texte et numériques émettent `focus` et `blur`, et les champs de choix utilisent
  `change`. Aucun contrôle intégré n’émet `click` : déclenchez-le donc avec le contrôleur.

### Le contrôleur d’événements

`onEventController` reçoit un contrôleur après l’initialisation du formulaire, et `null` lorsque ce
contrôleur est retiré :

- `dispatch({ type, fieldKey?, instancePath?, scopeId?, metadata? })` renvoie une promesse avec
  `status`, `operations`, `validationIssues` et `issues`, une fois les opérations acceptées
  terminées.
- `prepareSave({ intent: "submit" | "draft", instancePath?, scopeId? })` renvoie une promesse avec
  `eligible`, `payload`, `meta`, `validationSummary` et `issues`. Elle ne sauvegarde et ne ferme
  jamais rien.

Les écouteurs de champ utilisent `data_name`, et les chemins utilisent les clés du schéma et les
identifiants de ligne. Un chemin par position exige le `scopeId` actif des diagnostics. Les cibles
fermées et les contrôleurs retirés sont rejetés.

### Validation personnalisée

`INVALID(message)` ajoute un message à un enregistrement ou à une ligne pendant `validate-record` ou
`validate-repeatable`. Les messages rejoignent la liste de validation et sa navigation, sont
remplacés à chaque tentative et s’effacent lorsque les données changent ou que l’éditeur se ferme.
Ils n’entrent jamais dans `state.errors`, les diagnostics de calcul, les valeurs ou les métadonnées
de l’enregistrement.

Les gestionnaires de validation et de fermeture ne peuvent ni modifier de valeurs, ni afficher
d’alertes, ni renvoyer de promesses. Les gestionnaires de ligne peuvent lire les champs actuels de
l’enregistrement principal et des parents, mais `SETVALUE` écrit seulement dans leur propre ligne,
et les collections répétables sont hors de portée.

### Comment une sauvegarde est préparée

1. Attendre les mises à jour en cours.
2. Valider.
3. Exécuter `save-record` ou `save-repeatable` une fois, si la validation le permet.
4. Attendre la fin de ses opérations.
5. Valider de nouveau si des valeurs ont changé.
6. Construire l’enregistrement à partir de ce snapshot final.

La soumission et l’acceptation d’une ligne s’arrêtent en cas d’échec de validation. Un brouillon de
l’enregistrement principal continue avec `hasErrors: true`, et les lignes n’ont pas de brouillons.
Si un gestionnaire échoue, aucun `payload` n’est renvoyé. `isDraft` décrit l’action en cours, et
`isValid` la validité intégrée. Les diagnostics de calcul seuls ne bloquent jamais une sauvegarde.

### Quand les événements s’exécutent

Les modifications de l’utilisateur émettent `change` une fois les mises à jour terminées. Les
changements de ligne acceptés ajoutent `action` (`add`, `edit` ou `remove`) et
`affectedInstancePath`. Un champ de statut activé émet `change-status` seulement pour les
modifications de l’utilisateur. Les valeurs par défaut, `SETVALUE` et les calculs n’émettent pas
`change`. form0 attend le travail asynchrone de `onOperations` et `applyDefault`. Le repli expire
avec son déclenchement.

Une annulation confirmée exécute l’événement d’annulation, puis celui de déchargement. Une fermeture
réussie exécute l’événement de déchargement avant le retrait de l’éditeur. Si votre application
ferme directement un éditeur, déclenchez l’événement de déchargement avant de le démonter. Les
nouveaux rendus, les réinitialisations, le nettoyage de React Strict Mode et les démontages forcés
ne comptent pas comme une fermeture. `save-record` et `save-repeatable` s’exécutent avant la
sauvegarde, et il n’existe pas d’événements de schéma `saved-*`. Votre application gère la
sauvegarde, les messages de réussite et la fermeture.

Les envois `File` et `Blob` conservent leurs métadonnées standard et leur contenu. Leurs propriétés
personnalisées ne sont pas conservées.

## Rapports d’événements en échec

`eventDiagnostics` contrôle les rapports de console des événements en échec, séparément de
`submissionDiagnostics` :

```jsx
<FormRenderer
  schema={schema}
  engineOptions={{ events: { recordKind: "existing" } }}
  eventDiagnostics={{ failures: true }}
  submissionDiagnostics={{ saveFailures: true, validationBlocks: false }}
/>
```

Un événement en échec journalise un `console.error` par défaut, y compris un `SETVALUE()` rejeté et
une promesse `onOperations` rejetée. Le rapport contient le type d’événement, le champ, la portée de
l’enregistrement principal ou de la ligne, ainsi que les codes et messages des problèmes. Il ne
contient ni valeurs, ni arguments d’opération, ni snapshots, ni identifiants d’enregistrement.
Définissez `failures: false` si votre application gère ces rapports. Le réglage est mis à jour dans
les éditeurs ouverts et les opérations en cours.

Les messages de validation et `INVALID()` ne sont pas des échecs, et le travail annulé reste
silencieux. **Submit** et **Save** d’une ligne utilisent les rapports de soumission : vous n’en
recevez donc pas deux. Si vous appelez directement `prepareSave()`, inspectez son résultat.
`dispatch()` renvoie son résultat même lorsque les rapports de console sont désactivés. Ces réglages
ne contrôlent pas les avertissements de `form0-core` ni la sortie console avec `lifecycle: false`.

Les champs numériques acceptent des nombres, comme `SETVALUE("quantity", 1)`. Les champs de choix
acceptent des identifiants textuels : `SETVALUE("rating", "1")` pour une sélection unique et
`SETVALUE("tags", ["1"])` pour une sélection multiple. Un appel rejeté laisse tout son lot non
appliqué. Les rapports ne modifient ni les valeurs, ni la validation, ni les enregistrements, ni le
nombre d’évaluations.

### Essayez

1. Dans un schéma avec un `SingleChoiceField` nommé `rating`, ajoutez ce gestionnaire à
   `form.events.code` :

   ```js
   ON("load-record", function () {
     SETVALUE("rating", 1)
   })
   ```

1. Ouvrez le formulaire. **rating** reste vide, et la console affiche
   `[form0-react-native] Event failed.`

1. Remplacez `1` par l’identifiant textuel d’un des choix du champ, puis rouvrez le formulaire. Le
   choix est sélectionné, et la console n’affiche aucun rapport.
