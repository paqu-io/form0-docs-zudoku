## Valori iniziali e valori prioritari

Usa `initialValues` per il record in modifica. `overrideValues` ha la precedenza ed è utile per i
valori che devono prevalere lato host, come uno stato fornito dall'applicazione.

Per un ripristino completo, preferisci `initialSnapshot`:

```jsx
<FormRenderer
  engineOptions={{ events: { recordKind: "existing" } }}
  schema={schema}
  initialSnapshot={{
    raw_values: saved.raw_values,
    repeatable: saved.repeatable,
    timestamps: saved.timestamps,
  }}
  onSnapshotChange={(snapshot, change) => {
    if (change.dirty) queueDraft(snapshot)
  }}
  onSubmit={saveRecord}
/>
```

Uno snapshot iniziale sostituisce `initialValues` per i valori grezzi dei campi. Ripristina anche le
voci ripetibili annidate e i timestamp di client e server come un unico stato coerente.

## Errori di salvataggio e messaggi della console

Se il callback `onSubmit` fallisce, per impostazione predefinita viene scritto un rapporto in
`console.error`, con la fase del fallimento e l’errore originale. Se il callback di persistenza
rifiuta l’operazione, le modifiche restano disponibili per riprovare e il salvataggio non viene
confermato. Mostra un messaggio utile nella tua applicazione e rilancia l’errore; terminare normalmente
o intercettarlo senza rilanciarlo equivale a un salvataggio riuscito.

`submissionDiagnostics` controlla questi messaggi della console:

```jsx
<FormRenderer
  schema={schema}
  engineOptions={{ events: { recordKind: "new" } }}
  submissionDiagnostics={{ saveFailures: true, validationBlocks: false }}
  onSubmit={saveRecord}
/>
```

- `saveFailures` è `true` per impostazione predefinita. Usa `false` se l’applicazione segnala già gli errori.
- `validationBlocks` è `false` per impostazione predefinita. Usa `true` per registrare i tentativi
  bloccati di Submit e di Save nelle righe ripetibili. Un campo obbligatorio vuoto blocca la
  validazione; non è un’eccezione di salvataggio.

Le impostazioni restano aggiornate, anche durante un salvataggio in corso. Sono indipendenti da
`debug`, `engineOptions.diagnostics.console` e dal ciclo di vita. I rapporti non aggiungono valori del
modulo, snapshot o percorsi dei record. Gli errori di preparazione includono i codici e i messaggi dei
problemi. Annullare una conferma non genera messaggi; un’eccezione del callback viene segnalata come
fallimento del callback. I messaggi esistenti del nucleo mantengono il proprio comportamento.

Prova con un campo obbligatorio: premi Submit lasciandolo vuoto. Appare il messaggio di validazione e
la console resta silenziosa. Attiva `validationBlocks` e premi di nuovo Submit: appare una riga sul
blocco di validazione. Compila il campo, modifica temporaneamente `saveRecord` per lanciare
`new Error("Example save failure")` e premi Submit: appare un rapporto dell’errore e i valori modificati restano disponibili
per riprovare.

Questi controlli riguardano le azioni integrate del renderer. Le applicazioni che chiamano direttamente
`prepareSave()` devono esaminare e segnalare il risultato restituito.

## Osservare le bozze

`onSnapshotChange(snapshot, change)` viene chiamato prima con `{ kind: "seed", dirty: false }`. Le
modifiche successive dell'utente usano `{ kind: "change", dirty: boolean }`.

Lo snapshot contiene:

```js
{
  raw_values: {},
  repeatable: {},
  timestamps: {
    created_at_client: null,
    updated_at_client: null,
    created_at_server: null,
    updated_at_server: null,
  },
}
```

## Inviare i record

`onSubmit(record, meta)` riceve il record strutturato descritto in
[Output e record](/it/core/output-records). `meta` contiene `rawValues`, `repeatable`, `timestamps`
e `validationSummary`.

Se `onSubmit` restituisce una promise, un overlay configurato con `autoCloseOverlayOnSubmit` si
chiude solo dopo la risoluzione della promise. In caso di rifiuto resta aperto. Usa
`submitBlockedReason` per i requisiti dell'applicazione esterni allo schema e `externalDirty` per lo
stato dell'applicazione esterno al renderer.

## API degli eventi gestiti

Vedi il controller e il contratto degli ambiti in [FormRenderer](/it/bindings/react/form-renderer).

`engineOptions.events`: `lifecycle` (true), `recordKind` obbligatorio (new/existing), `fieldInteractions` ([focus, blur, click]). Usa `lifecycle: false` per il ciclo legacy o `fieldInteractions: []` per disabilitare le interazioni automatiche.
`engineOptions.onEventController(controller | null)`: `dispatch(request)`, `prepareSave(request)`.

La preparazione non persiste né chiude. Le bozze radice mantengono i risultati nel riepilogo; submit normale e accettazione delle righe sono bloccati dalla validazione. I diagnostici di calcolo restano separati. Nessuna valutazione o aggregazione delle righe chiuse.

## Revisione dei calcoli figli e persistenza

L’invio ordinario aggiorna automaticamente i calcoli figli chiusi se l’impostazione è omessa.
`form.repeatable_recalculation: 'confirm'` richiede revisione. L’host può imporla con `mode: 'confirm'`,
ma `automatic` non può ridurre il requisito del modulo. `allowRetain` è un permesso esplicito e non
attiva da solo la conferma. La scelta riguarda tutti i figli interessati o nessuno. La preparazione
radice è rifiutata se rimane un editor figlio non accettato.

La revisione mostra titoli/percorsi, etichette, vecchi/nuovi valori e conteggi in pagine limitate.
Personalizza i testi con `submissionOptions.messages`. Tutti gli esiti di validazione restano
disponibili con i percorsi; l’interfaccia li pagina e porta al record o campo interessato. Gli esiti
personalizzati di ambito appartengono al record, senza attribuirli a un campo inventato.

```jsx
<FormRenderer
  engineOptions={{ events: { recordKind: "existing" } }}
  schema={schema}
  initialSnapshot={savedSnapshot}
  initialFreshness={savedFreshness}
  submissionOptions={{ mode: "confirm", allowRetain: true }}
  onSubmit={async (record, meta) => {
    await storage.save({ record, freshness: meta.freshness })
  }}
/>
```

Il completamento corretto del callback riconosce la persistenza. Salva insieme record selezionato e
compagno di freschezza prima di risolvere; genera un errore o rifiuta in caso di fallimento o
annullamento. Scegliere `20 → 24` conserva `24` come lavoro non salvato se validazione o persistenza
falliscono dopo. La freschezza resta fuori dai valori salvati. Ripristinala con `initialFreshness`;
riconoscimenti vecchi non cancellano stati in sospeso nuovi. Con totali mantenuti `[110,220]`, la somma
inviata è `330`, mai il `360` della proposta aggiornata.

I controller di preparazione non aprono dialoghi né salvano dati. Controlla `eligible`, gestisci
`requires_decision` con `payload: null` e riconosci solo il `preparationId` salvato correttamente.
Le pagine contengono 50 modifiche per impostazione predefinita e al massimo 100. Continua con
`prepareSave()` e `decision: { reviewId, action: 'refresh' | 'retain' | 'cancel' }`. Input/configurazioni
modificati o una nuova preparazione invalidano la revisione. La validazione precede l’hook di
salvataggio, eseguito una volta; le sue scritture possono richiedere revisione senza ripetere l’hook.

```js
const prepared = await controller.prepareSave({ intent: "submit", signal })
if (prepared.status === "requires_decision") {
  const page = await controller.getSaveChanges({
    preparationId: prepared.preparationId,
    offset: 0,
    limit: 50,
  })
  showReview(prepared, page)
} else if (prepared.eligible) {
  await storage.save({ record: prepared.payload, freshness: prepared.meta.freshness })
  controller.acknowledgeSave({ preparationId: prepared.preparationId })
}
```

I worker conservano revisioni e report internamente. Le risposte ordinarie contengono dati selezionati e riepiloghi; i dettagli vengono richiesti in pagine limitate. Gli helper di tipo funzione restano esclusi dai worker. Segnali e callback non vengono inviati nei messaggi di clonazione strutturata.

I setter programmatici usano il contratto rigoroso condiviso. Valori iniziali e sostituzioni dell’host restano percorsi di caricamento tolleranti, anche nella vista, che conserva i calcoli accettati. Vedi il contratto di aggiornamento dei valori. [Vedi il contratto di aggiornamento dei valori](/it/core/engine/value-updates).
