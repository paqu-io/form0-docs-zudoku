`FormRenderer` valida e prepara uno schema, crea il motore del modulo, esegue il rendering di campi e
sezioni nativi e produce record strutturati o snapshot ripristinabili.

```jsx
<FormRenderer
  engineOptions={{ events: { recordKind: "new" } }}
  schema={schema}
  initialValues={{ name: "Ada" }}
  mode="edit"
  colorMode="light"
  labelPosition="top"
  onSubmit={saveRecord}
/>
```

## Proprietà essenziali

| Proprietà               | Scopo                                                                                                                                                                                                              |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `schema`                | Uno schema form0 che contiene `form.elements`.                                                                                                                                                                     |
| `initialValues`         | Valori iniziali dei campi non ripetibili.                                                                                                                                                                          |
| `initialSnapshot`       | Ripristina insieme valori grezzi, stato delle sezioni ripetibili e timestamp.                                                                                                                                      |
| `overrideValues`        | Applica valori prioritari sopra quelli iniziali.                                                                                                                                                                   |
| `onSubmit`              | Riceve il record strutturato e i relativi metadati, solo se la validazione riesce.                                                                                                                                 |
| `submissionDiagnostics` | Controlla gli errori di salvataggio (attivi) e i messaggi di blocco della validazione (disattivi).                                                                                                                 |
| `submissionOptions`     | Imposta le opzioni di revisione, i messaggi e `validateHiddenValues`.                                                                                                                                              |
| `onResolveHiddenValue`  | Consente alla tua applicazione di [correggere un valore nascosto](/it/bindings/react-native/values-snapshots-submission#risolvere-un-valore-nascosto-che-non-supera-la-validazione) che non supera la validazione. |
| `initialFreshness`      | Ripristina il `freshness` salvato di un record.                                                                                                                                                                    |
| `eventDiagnostics`      | Controlla i report degli eventi non riusciti (attivi).                                                                                                                                                             |
| `onSave`                | Riceve uno snapshot senza richiedere che il modulo sia valido.                                                                                                                                                     |
| `onSnapshotChange`      | Osserva gli snapshot iniziali e quelli delle modifiche dell'utente.                                                                                                                                                |
| `mode`                  | Avvia in modalità `edit` o `readonly`.                                                                                                                                                                             |
| `repeatableEntryMode`   | Apertura delle [righe di sezioni ripetibili](/it/core/fields/containers#repeatablesection) esistenti: `readonly` (predefinito) o `edit`; le nuove si aprono in modifica.                                           |

## Integrazione con la tua applicazione

- `onRequestClose` abilita l'azione di annullamento principale e riceve `{ reason: "cancel" }` dopo
  l'eventuale conferma di abbandono.
- `headerAccessory` esegue il rendering di contenuti dell'applicazione subito sotto l'intestazione
  integrata.
- `showHeader` nasconde l'intestazione integrata quando la tua applicazione fornisce la navigazione
  e le azioni circostanti.
- `primaryActionMode`, `primaryActionLabel` e `showPrimaryActionsInViewMode` personalizzano l'azione
  principale integrata.
- `onSchemaReady` riceve lo schema preparato dopo che sono state garantite chiavi stabili.
- `engineOptions` fornisce gli helper del nucleo, la configurazione di sicurezza, gli avvisi, la
  gestione delle operazioni e l'osservazione degli aggiornamenti.

I gestori di eventi dello schema vengono eseguiti su Hermes se sono scritti come funzioni o arrow
function in `form.events.code`. Consulta
[Come viene eseguito il codice dei gestori](/it/core/engine/events-operations#come-viene-eseguito-il-codice-dei-gestori).

Prosegui con [Valori, snapshot e invio](/it/bindings/react-native/values-snapshots-submission)
oppure [Modalità e navigazione](/it/bindings/react-native/modes-navigation).

## Opzioni del motore e diagnostica dei calcoli

`engineOptions` passa helper, impostazioni di sicurezza, `onWarning`, `onUpdate`, `onOperations` e
le impostazioni di diagnostica dei calcoli al motore principale e ai motori di riga. Gli helper e la
sicurezza vengono impostati alla creazione del motore, quindi rimonta `FormRenderer` per cambiarli.
Le callback e l'impostazione della console si aggiornano negli editor aperti senza un'altra
valutazione.

```jsx
const findingsByScope = new Map()

;<FormRenderer
  schema={schema}
  engineOptions={{
    events: { recordKind: "new" },
    diagnostics: { console: false },
    onDiagnostics(snapshot, meta) {
      if (meta.kind === "scope-ended") findingsByScope.delete(meta.scopeId)
      else findingsByScope.set(meta.scopeId, { snapshot, meta })
    },
  }}
/>
```

I report della console sono attivi per impostazione predefinita. `diagnostics.console: false`
disattiva nella console i dettagli dei calcoli e i messaggi di ripristino e di fine ambito, mentre
la raccolta e le callback continuano. Aggiungere `onDiagnostics` non disattiva i report della
console. I titoli della console sono in inglese.

`onDiagnostics(snapshot, meta)` riceve una copia dei risultati dopo ogni valutazione completata,
compresa la prima, i risultati ripetuti e `[]` dopo un ripristino. La console salta le ripetizioni
identiche e riporta i risultati nuovi o modificati, il ripristino e i problemi che si ripresentano.
Un errore nella tua callback, compresa una promise rifiutata, non può interrompere la valutazione.

`meta` contiene `scopeId`, `instancePath`, `evaluationId` e `kind`. Un ambito è la durata di un
motore, e gli identificatori di valutazione aumentano al suo interno. Il percorso del record
principale è `[]`. Ogni segmento di riga ha `repeatableKey`, `instanceId`, un `index` che parte da
zero e `identity: "id" | "position"`. form0 usa l'`id` o il `record_id` di una riga e, in mancanza,
la sua posizione. I risultati riportano lo stesso percorso in `context.instancePath`. I report non
creano mai identificatori di record.

Chiudere o eliminare un editor, sostituirne il motore o lo schema, o smontarlo termina l'ambito con
`onDiagnostics([], { ...meta, kind: "scope-ended" })`. Questo significa che l'ambito non è più
osservato, non che la riga si è ripristinata. Vengono riportati solo i motori che valutano, quindi
questa callback non è un report completo dello stato e non valuta di nuovo le righe chiuse.

La diagnostica dei calcoli resta fuori da `state.errors`, dagli snapshot salvati e dai record. Non
cambia la validazione, l'invio o il salvataggio delle bozze, e non aggiunge avvisi o pannelli.

### Gestire operazioni e avvisi

`onOperations(operations, meta, applyDefault)` riceve tutte le operazioni tranne gli avvisi. Passa
quelle da gestire normalmente ad `applyDefault(selected, meta)`. Senza la callback si applica la
gestione predefinita. Il renderer mostra ogni `ALERT` una volta. La tua callback deve gestire ogni
lotto che riceve.

`onWarning` riceve gli avvisi del motore, che possono essere limitati, e non sostituisce
`onDiagnostics`. `onUpdate(state, engine)` riceve lo stato e un oggetto motore il cui tipo dipende
da come viene eseguito il modulo. Se ti serve solo la diagnostica, usa `onDiagnostics`.

## Eventi e validazione personalizzata

Gli eventi del ciclo di vita e le interazioni dei campi sono attivi per impostazione predefinita.
Usa `recordKind` per indicare se il modulo contiene un record nuovo o esistente:

```jsx
<FormRenderer
  schema={schema}
  engineOptions={{
    events: { recordKind: "existing" },
    onEventController: (controller) => {
      controllerRef.current = controller
    },
  }}
/>
```

`recordKind` deve essere `new` o `existing`, a meno che tu non imposti `lifecycle: false`. form0 non
lo ricava dai valori. Queste impostazioni durano per tutta la vita dell'editor, quindi rimontalo per
cambiare `recordKind`, `lifecycle`, gli helper o la sicurezza. Le callback restano attive.

- Un modulo in sola lettura esegue `load-record`. Un modulo in modifica esegue `load-record` e poi
  `new-record` o `edit-record`.
- Le righe aperte usano gli eventi ripetibili, a seconda che siano nuove o esistenti.
- `lifecycle: false` mantiene solo `load-record`, `edit-record` e `change` per il record principale.
  `fieldInteractions: []` disattiva le interazioni automatiche.
- I campi di testo e numerici emettono `focus` e `blur`, mentre i campi di scelta usano `change`.
  Nessun controllo integrato emette `click`, quindi attivalo con il controller.

### Il controller degli eventi

`onEventController` riceve un controller dopo l'inizializzazione del modulo, e `null` quando quel
controller viene ritirato:

- `dispatch({ type, fieldKey?, instancePath?, scopeId?, metadata? })` restituisce una promise con
  `status`, `operations`, `validationIssues` e `issues`, al termine delle operazioni accettate.
- `prepareSave({ intent: "submit" | "draft", instancePath?, scopeId? })` restituisce una promise con
  `eligible`, `payload`, `meta`, `validationSummary` e `issues`. Non salva e non chiude mai nulla.

I listener dei campi usano `data_name`, e i percorsi usano le chiavi dello schema e gli
identificatori di riga. Un percorso per posizione richiede lo `scopeId` attivo dalla diagnostica. Le
destinazioni chiuse e i controller ritirati vengono rifiutati.

### Validazione personalizzata

`INVALID(message)` aggiunge un messaggio a un record o a una riga durante `validate-record` o
`validate-repeatable`. I messaggi entrano nell'elenco di validazione e nella sua navigazione,
vengono sostituiti a ogni tentativo e si cancellano quando i dati cambiano o l'editor si chiude. Non
entrano mai in `state.errors`, nella diagnostica dei calcoli, nei valori o nei metadati del record.

I gestori di validazione e di chiusura non possono cambiare valori, mostrare avvisi o restituire
promise. I gestori di riga possono leggere i campi attuali del record principale e dei genitori, ma
`SETVALUE` scrive solo nella propria riga, e le raccolte ripetibili sono fuori portata.

### Come viene preparato un salvataggio

1. Attende gli aggiornamenti in sospeso.
2. Valida.
3. Esegue `save-record` o `save-repeatable` una volta, se la validazione lo consente.
4. Attende il termine delle sue operazioni.
5. Valida di nuovo se sono cambiati dei valori.
6. Costruisce il record da quello snapshot finale.

L'invio e l'accettazione di una riga si fermano in caso di errori di validazione. Una bozza del
record principale prosegue con `hasErrors: true`, e le righe non hanno bozze. Se un gestore
fallisce, non viene restituito alcun `payload`. `isDraft` descrive l'azione corrente, e `isValid` è
la validità integrata. La diagnostica dei calcoli da sola non blocca mai un salvataggio.

### Quando vengono eseguiti gli eventi

Le modifiche dell'utente emettono `change` al termine degli aggiornamenti. Le modifiche di riga
accettate aggiungono `action` (`add`, `edit` o `remove`) e `affectedInstancePath`. Un campo di stato
attivo emette `change-status` solo per le modifiche dell'utente. I valori predefiniti, `SETVALUE` e
i calcoli non emettono `change`. form0 attende il lavoro asincrono di `onOperations` e
`applyDefault`. Il fallback scade con la sua attivazione.

Un annullamento confermato esegue l'evento di annullamento e poi quello di scaricamento. Una
chiusura riuscita esegue l'evento di scaricamento prima di rimuovere l'editor. Se la tua
applicazione chiude direttamente un editor, attiva l'evento di scaricamento prima di smontarlo. I
nuovi rendering, i reset, la pulizia di React Strict Mode e gli smontaggi forzati non contano come
chiusura. `save-record` e `save-repeatable` vengono eseguiti prima del salvataggio, e non esistono
eventi di schema `saved-*`. La tua applicazione gestisce il salvataggio, i messaggi di conferma e la
chiusura.

I caricamenti `File` e `Blob` conservano i metadati standard e il contenuto. Le loro proprietà
personalizzate non vengono conservate.

## Report degli eventi non riusciti

`eventDiagnostics` controlla i report della console per gli eventi non riusciti, separatamente da
`submissionDiagnostics`:

```jsx
<FormRenderer
  schema={schema}
  engineOptions={{ events: { recordKind: "existing" } }}
  eventDiagnostics={{ failures: true }}
  submissionDiagnostics={{ saveFailures: true, validationBlocks: false }}
/>
```

Un evento non riuscito registra un `console.error` per impostazione predefinita, compresi un
`SETVALUE()` rifiutato e una promise `onOperations` rifiutata. Il report contiene il tipo di evento,
il campo, l'ambito del record principale o della riga, e i codici e i messaggi dei problemi. Non
contiene valori, argomenti delle operazioni, snapshot o identificatori di record. Imposta
`failures: false` se la tua applicazione gestisce questi report. L'impostazione si aggiorna negli
editor aperti e nelle operazioni in sospeso.

I messaggi di validazione e `INVALID()` non sono errori, e il lavoro annullato non riporta nulla.
**Submit** e **Save** di una riga usano i report di invio, quindi non ne ricevi due. Se chiami
direttamente `prepareSave()`, ispeziona il risultato. `dispatch()` restituisce il risultato anche
quando i report della console sono disattivati. Queste impostazioni non controllano gli avvisi di
`form0-core` né l'output della console con `lifecycle: false`.

I campi numerici accettano numeri, come `SETVALUE("quantity", 1)`. I campi di scelta accettano
identificatori testuali: `SETVALUE("rating", "1")` per la selezione singola e
`SETVALUE("tags", ["1"])` per la selezione multipla. Una chiamata rifiutata lascia non applicato
l'intero lotto. I report non cambiano valori, validazione, record o conteggi delle valutazioni.

### Prova

1. In uno schema con un `SingleChoiceField` chiamato `rating`, aggiungi questo gestore a
   `form.events.code`:

   ```js
   ON("load-record", function () {
     SETVALUE("rating", 1)
   })
   ```

1. Apri il modulo. **rating** resta vuoto, e la console mostra `[form0-react-native] Event failed.`

1. Sostituisci `1` con l'identificatore testuale di una delle scelte del campo e apri di nuovo il
   modulo. La scelta risulta selezionata, e la console non mostra alcun report.
