## Stato iniziale e ripristino

Usa `initialValues` per inizializzare un record nel modo consueto. `overrideValues` ha la precedenza
ed è utile per i valori che devono prevalere lato host. Per un ripristino completo, preferisci
`initialSnapshot`:

```jsx
<FormRenderer
  engineOptions={{ events: { recordKind: "existing" } }}
  schema={schema}
  initialSnapshot={savedDraft}
  onSnapshotChange={(snapshot, change) => {
    if (change.dirty) queueLocalDraft(snapshot)
  }}
  onSubmit={uploadRecord}
/>
```

Lo snapshot mantiene insieme valori grezzi, voci ripetibili annidate e timestamp:

```js
{
  raw_values: {},
  repeatable: {},
  timestamps: {
    created_at_client: null,
    updated_at_client: null,
    created_at_server: null,
    updated_at_server: null,
  },
}
```

`onSnapshotChange(snapshot, meta)` segnala prima `{ kind: "seed", dirty: false }`; le modifiche
successive dell'utente usano `{ kind: "change", dirty }`.

## Errori di salvataggio e messaggi della console

Quando un salvataggio non riesce, `FormRenderer` conserva i valori dell'utente perché possa
riprovare e scrive un rapporto in `console.error` con la fase dell'errore e l'errore originale. Non
mostra alcun messaggio all'utente, quindi fallo nella tua applicazione e poi rilancia l'errore:

```jsx
async function handleSubmit(record) {
  try {
    await saveRecord(record)
  } catch (error) {
    setMessage("The record was not saved. Try again.")
    throw error
  }
}
```

Se intercetti l'errore senza rilanciarlo, `FormRenderer` considera riuscito il salvataggio.

`submissionDiagnostics` controlla questi messaggi della console:

```jsx
<FormRenderer
  schema={schema}
  engineOptions={{ events: { recordKind: "new" } }}
  submissionDiagnostics={{ saveFailures: true, validationBlocks: false }}
  onSubmit={handleSubmit}
/>
```

- `saveFailures` è attivo per impostazione predefinita. Impostalo su `false` se l'applicazione
  segnala già gli errori.
- `validationBlocks` è disattivato per impostazione predefinita. Impostalo su `true` per registrare
  una riga ogni volta che la validazione blocca **Submit** o **Save** su una riga ripetibile.

Un campo obbligatorio vuoto è un blocco di validazione, non un errore di salvataggio.

### Prova

1. Tocca **Submit** con un campo obbligatorio vuoto. Il campo mostra il suo messaggio di validazione
   e la console resta silenziosa.
2. Aggiungi `validationBlocks: true` e tocca di nuovo **Submit**. La console mostra
   `[form0-react-native] Submit blocked by validation.`
3. Compila il campo, fai in modo che `saveRecord` generi `new Error("Example save failure")` e tocca
   **Submit**. La console mostra `[form0-react-native] Submit failed during onSubmit.` con il tuo
   errore, e i valori restano nel modulo.
4. Rimuovi il `throw` e tocca di nuovo **Submit**. Il salvataggio riesce.

### Dettagli

- Queste impostazioni si applicano subito, anche durante un salvataggio in corso. Sono indipendenti
  da `debug`, `engineOptions.diagnostics.console` e dalle impostazioni del ciclo di vita.
- I rapporti non includono valori del modulo, snapshot o percorsi dei record. Gli errori di
  preparazione includono i relativi codici e messaggi.
- Annullare una conferma non scrive nulla nella console. Un'eccezione generata dal tuo callback
  viene segnalata come errore del callback.
- `form0-core` scrive le proprie righe, come `[EVENT HANDLER] Registered`. Queste impostazioni non
  le controllano.
- Queste impostazioni coprono le azioni integrate del renderer. Se chiami direttamente
  `prepareSave()`, controlla il risultato restituito.
- Le stesse impostazioni valgono per gli errori di `onSave` nelle bozze. Le bozze non valide restano
  salvabili e una bozza salvata correttamente non registra alcun blocco di validazione.

## Salvare bozze o inviare record

Imposta `primaryActionMode="save"` e fornisci `onSave(snapshot, meta)` per un'azione di salvataggio
delle bozze che non richiede il superamento della validazione. `meta` contiene il riepilogo della
validazione corrente e lo stato delle modifiche non salvate.

L'azione di invio predefinita esegue prima la validazione. `onSubmit(record, meta)` riceve il record
strutturato descritto in [Output e record](/it/core/output-records), insieme ai valori grezzi, allo
stato delle sezioni ripetibili, ai timestamp e al riepilogo della validazione.

Il binding non rende persistenti né sincronizza nessuno dei due contenuti. Memorizza gli snapshot in
locale, carica i record, ripeti i tentativi non riusciti e risolvi i conflitti nell'applicazione
host.

## API degli eventi gestiti

Vedi il controller e il contratto degli ambiti in [FormRenderer](/it/bindings/react-native/form-renderer).

`engineOptions.events`: `lifecycle` (true), `recordKind` obbligatorio (new/existing), `fieldInteractions` ([focus, blur, click]). Usa `lifecycle: false` per il ciclo legacy o `fieldInteractions: []` per disabilitare le interazioni automatiche.
`engineOptions.onEventController(controller | null)`: `dispatch(request)`, `prepareSave(request)`.

La preparazione non persiste né chiude. Le bozze radice mantengono i risultati nel riepilogo; submit normale e accettazione delle righe sono bloccati dalla validazione. I diagnostici di calcolo restano separati. Nessuna valutazione o aggregazione delle righe chiuse.

## Revisione dei calcoli figli e persistenza

L’invio ordinario aggiorna automaticamente i calcoli figli chiusi se l’impostazione è omessa.
`form.repeatable_recalculation: 'confirm'` richiede revisione. L’host può imporla con `mode: 'confirm'`,
ma `automatic` non può ridurre il requisito del modulo. `allowRetain` è un permesso esplicito e non
attiva da solo la conferma. La scelta riguarda tutti i figli interessati o nessuno. La preparazione
radice è rifiutata se rimane un editor figlio non accettato.

La revisione mostra titoli/percorsi, etichette, vecchi/nuovi valori e conteggi in pagine limitate.
Personalizza i testi con `submissionOptions.messages`. Tutti gli esiti di validazione restano
disponibili con i percorsi; l’interfaccia li pagina e porta al record o campo interessato. Gli esiti
personalizzati di ambito appartengono al record, senza attribuirli a un campo inventato.

```jsx
<FormRenderer
  engineOptions={{ events: { recordKind: "existing" } }}
  schema={schema}
  initialSnapshot={savedSnapshot}
  initialFreshness={savedFreshness}
  submissionOptions={{ mode: "confirm", allowRetain: true }}
  onSubmit={async (record, meta) => {
    await storage.save({ record, freshness: meta.freshness })
  }}
/>
```

Il completamento corretto del callback riconosce la persistenza. Salva insieme record selezionato e
compagno di freschezza prima di risolvere; genera un errore o rifiuta in caso di fallimento o
annullamento. Scegliere `20 → 24` conserva `24` come lavoro non salvato se validazione o persistenza
falliscono dopo. La freschezza resta fuori dai valori salvati. Ripristinala con `initialFreshness`;
riconoscimenti vecchi non cancellano stati in sospeso nuovi. Con totali mantenuti `[110,220]`, la somma
inviata è `330`, mai il `360` della proposta aggiornata.

I controller di preparazione non aprono dialoghi né salvano dati. Controlla `eligible`, gestisci
`requires_decision` con `payload: null` e riconosci solo il `preparationId` salvato correttamente.
Le pagine contengono 50 modifiche per impostazione predefinita e al massimo 100. Continua con
`prepareSave()` e `decision: { reviewId, action: 'refresh' | 'retain' | 'cancel' }`. Input/configurazioni
modificati o una nuova preparazione invalidano la revisione. La validazione precede l’hook di
salvataggio, eseguito una volta; le sue scritture possono richiedere revisione senza ripetere l’hook.

```js
const prepared = await controller.prepareSave({ intent: "submit", signal })
if (prepared.status === "requires_decision") {
  const page = await controller.getSaveChanges({
    preparationId: prepared.preparationId,
    offset: 0,
    limit: 50,
  })
  showReview(prepared, page)
} else if (prepared.eligible) {
  await storage.save({ record: prepared.payload, freshness: prepared.meta.freshness })
  controller.acknowledgeSave({ preparationId: prepared.preparationId })
}
```

`prepareSave({ intent: 'draft' })` radice e il salvataggio bozze Native mantengono i calcoli figli
accettati senza dialogo. Gli errori ordinari vengono riportati e consentono una bozza radice; i
fallimenti di esecuzione la impediscono. Applica a `onSave` lo stesso contratto record-compagno.
Una scrittura locale duratura è distinta dalla successiva sincronizzazione con il server.

I setter programmatici usano il contratto rigoroso condiviso. Valori iniziali e sostituzioni dell’host restano percorsi di caricamento tolleranti, anche nella vista, che conserva i calcoli accettati. [Vedi il contratto di aggiornamento dei valori](/it/core/engine/value-updates).
