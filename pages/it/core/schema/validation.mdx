form0-core valida gli schemi prima di eseguire il motore. La validazione riguarda la struttura e la
correttezza degli attributi, non gli aspetti dell'interfaccia.

## Cosa viene validato

- Attributi obbligatori per ogni tipo di campo
- Valori consentiti per gli attributi (ad esempio, opzioni `display`)
- `key` e `data_name` unici
- Formato di `data_name` (minuscole a-z, 0-9, underscore, lunghezza massima 42)
- Conformità dei valori predefiniti alle regole del tipo di campo
- Validità degli operatori delle condizioni per il tipo di campo referenziato
- Struttura e chiavi consentite dei metadati IA

## Validazione in fase di esecuzione

In fase di esecuzione, ogni campo controlla il proprio valore quando il motore valuta il modulo. Il
risultato si trova nella mappa `errors` dello stato del motore.

| Campo           | Valore accettato                                                            | Controllato anche                                            |
| --------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `TextField`     | Una stringa                                                                 | `pattern`, se impostato                                      |
| `NumericField`  | Un numero finito                                                            | `min` e `max`, e i numeri interi quando `format` è `integer` |
| `DateField`     | Una data reale del calendario come `YYYY-MM-DD`, dall'anno `0001` al `9999` | Nient'altro                                                  |
| `TimeField`     | `HH:MM` o `HH:MM:SS`, con ore `00`–`23` e minuti e secondi `00`–`59`        | Nient'altro                                                  |
| Campi di scelta | Valori definiti in `choices`                                                | Nient'altro                                                  |

- form0 non converte i valori, quindi `"12"` in un `NumericField` è un errore.
- `null`, `undefined` e `""` contano come vuoti, non come tipo sbagliato. Un `TextField` facoltativo
  vuoto salta anche `pattern`.
- Un valore che non passa resta in `values` e compare in `errors`, quindi un record caricato si può
  ancora ispezionare e correggere.
- Questi controlli valgono per tutti i campi, compresi quelli nascosti.

### Prova

Ti serve [form0-cli](/it/cli/install-update).

1. Scarica un modulo con un `TextField`, un `NumericField` e un `DateField`:

   ```bash
   curl -o value-types.json https://docs.form0.dev/examples/value-types.form0.json
   ```

1. Eseguilo con valori corretti. L'output mostra `"errors": {}`:

   ```bash
   form0 run value-types.json --values '{"name":"Ada","age":36,"start":"2026-02-28"}'
   ```

1. Eseguilo con valori sbagliati:

   ```bash
   form0 run value-types.json --values '{"name":42,"age":"36","start":"2026-02-30"}'
   ```

   Ora ogni campo compare in `errors`:

   ```json
   "errors": {
     "name": "name must be a string",
     "age": "age must be a finite number",
     "start": "start must be a valid YYYY-MM-DD date"
   }
   ```

### Campi obbligatori e invio

Il motore calcola un indicatore `required` per ogni campo, ma non aggiunge un errore solo perché un
campo obbligatorio è vuoto. Il controllo dei campi obbligatori riguarda l'invio: i renderer ufficiali
combinano `visible`, `required` e il valore corrente, ignorano i campi nascosti e decidono quando
mostrare l'errore.

### Controllare un invio

`createRecordEvaluator().prepareSubmission()` esegue i calcoli, seleziona i valori da inviare e
applica gli stessi controlli dei renderer ufficiali. Usalo su un server o in qualsiasi applicazione
senza renderer. Vedi le sue opzioni in
[Preparare un invio](/it/core/engine/evaluation-cycle#preparare-un-invio).

Se hai già uno snapshot valutato, chiama
`validateSubmission({ schema, snapshot, validationIssues })`. Si limita a controllare: non ricalcola
nulla e non rimuove i campi sconosciuti.

Entrambi seguono le stesse regole:

- Per impostazione predefinita, i campi nascosti e i campi sotto genitori nascosti non bloccano un
  invio.
- Un campo obbligatorio visibile e vuoto blocca l'invio, anche se è in sola lettura.
- `0` e un **No** selezionato contano come compilati.
- Una [riga nascosta di una sezione ripetibile](/it/core/fields/containers#repeatablesection) non
  partecipa al controllo.
- Una bozza si può salvare con errori di validazione. Un gestore che fallisce durante l'esecuzione
  blocca anche le bozze.
- I gestori di validazione non possono cambiare valori o mostrare avvisi.
- Questi controlli non cambiano `state.errors`. `LabelField` e `CalculatedField` seguono regole
  proprie.

Il risultato include un `validationSummary`:

| Proprietà             | Contiene                                                                                   |
| --------------------- | ------------------------------------------------------------------------------------------ |
| `hasErrors`           | Se qualcosa non è andato a buon fine.                                                      |
| `requiredFieldErrors` | Campi obbligatori rimasti vuoti.                                                           |
| `generalErrors`       | Valori che non rispettano le regole del loro campo.                                        |
| `scopeIssues`         | Messaggi di `INVALID()`, che riguardano un record o una riga, non un campo.                |
| `orderedIssues`       | Tutto quanto sopra nell'ordine del record, con il record principale prima delle sue righe. |

Ogni risultato indica il campo con la chiave e il `data_name`, e la riga con `instancePath`. Un
messaggio di `INVALID()` del record principale resta sul record principale, perché form0 non può
sapere a quale campo si riferisce. `managedEvents: true` esegue anche i gestori di validazione delle
righe chiuse. Ogni riga con errori va corretta prima che l'invio passi, indipendentemente dal loro
numero.

Se un utente mantiene valori calcolati precedenti durante una
[revisione](/it/core/engine/evaluation-cycle#rivedere-le-righe-modificate), i controlli si applicano
a quei valori mantenuti, comprese le condizioni che ne dipendono.

### Controllare i valori nascosti su un server

Per impostazione predefinita, un invio ignora gli errori dei campi nascosti, perché l'utente non può
vederli. Un client che chiama la tua API può mettere qualsiasi cosa in quei campi, quindi attiva il
controllo nel codice del tuo server:

```js
const result = await evaluator.prepareSubmission(snapshot, { validateHiddenValues: true })
```

`validateSubmission()` accetta la stessa opzione. Quando è attiva, un valore nascosto che non
rispetta le proprie regole blocca l'invio, come un numero in un `TextField`. Questo include le righe
nascoste. Le altre regole non cambiano:

- Un campo obbligatorio nascosto e vuoto non blocca, e i gestori di validazione delle righe nascoste
  non vengono eseguiti.
- Una bozza si può ancora salvare con questi errori.
- Quando continui una revisione con `decision`, passa la stessa impostazione.

Ognuno di questi errori ha `hidden: true`. Per sostituire o cancellare il valore dal tuo codice,
consulta
[Risolvere un valore nascosto](/it/core/engine/evaluation-cycle#risolvere-un-valore-nascosto-che-non-supera-la-validazione).

Questo controllo copre solo i valori. Non rimuove i campi sconosciuti e non decide chi può inviare.
[Aggiungi un modulo a un'app React esistente](/it/guides/add-form-to-react-app) contiene un
esempio completo di server.

## Errori comuni

- Attributi obbligatori mancanti
- `key` o `data_name` duplicati
- Operatori non validi (ad esempio, `contains` su un campo numerico)
- Valori predefiniti che non corrispondono al tipo di campo
